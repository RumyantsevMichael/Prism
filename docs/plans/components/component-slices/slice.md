# Components for slices and verification

## Outcome

A repository declares its components, each planned leaf slice records one and stays inside it, verification runs its component's tests and the dependents' tests when a scope finishes, the review browser labels each slice's component, and a checkout that names a store but no repository is refused.

## Contract

The parent's accepted split fixes the component model in its Interfaces, and clauses 1-10 restate its clauses 1-10 word for word in meaning; clause 11 restates and extends its clause 11.
Its clause 12 stays true here, because no slice of this contract changes a native index.
The four product defaults of the parent apply: a verified change outside the component fails the run, the dependents' run covers every transitive dependent once per finished scope, it also runs for a scope inside one component, and a change under a shared path makes no component's dependents run.

1. A repository declares components under `## Components` in its committed `.prism/workflow.md` as top-level list items `- <name>: <folder>`, each optionally followed by more-indented list items `- Test command: <command>` and `- Depends on: <name>, <name>`; the labels `Test command`, `Depends on`, and `Shared paths` match without case and without a parenthesized note, as other sections' labels do, while a component name is read as written, and lines that are not list items are ignored.
2. A component name matches `^[a-z0-9](?:[a-z0-9_-]{0,62}[a-z0-9])?$`, the rule for repository names.
3. A folder is a project-relative path with forward slashes, read without a trailing `/`, and never empty, `.`, absolute, or holding a backslash, a colon, or an empty, `.`, or `..` segment; a declared folder that does not exist yet is accepted, so a design can declare the component that its slices create.
4. A top-level item `- Shared paths: <path>, <path>` under `## Components` lists project-relative files or folders under the same path rules, and a file lies under a shared path when it equals that path or lies inside it.
5. The root component is named after the repository: the `Repository` name under `## Workspace` when the configuration names a record store, and `root` otherwise.
6. The root component holds every file outside all declared folders, tests with the repository's `Test command` under `## Stack`, and depends on nothing, while a declared component may name it under `Depends on`.
7. A repository whose configuration lists no component under `## Components` declares no components and is one component, its root component, holding every file.
8. A file belongs to the declared component whose folder it lies inside, and otherwise to the root component; shared paths never change which component a file belongs to, only which files a slice may change.
9. Every operation that reads a repository's components refuses an invalid declaration with an error whose `code` and fields are listed below, which a tool call returns as a JSON-RPC error whose `data` holds the same `code` and fields; the operations that read components are `update_initiative` with an `accept_design` operation, directly, inside `propose_design`, or replayed by `accept_proposal`, `verify_slice` for a slice that records a component or with `dependents`, and the `update_roadmap` `ship` operation, and every other operation, such as `get_initiative`, `get_roadmap`, and the review browser, reads no components and is unaffected.
   - `component_invalid` refuses an entry with an invalid name or folder, an invalid shared path, a name declared twice or equal to the root component's name, an unknown nested label, or a nested item before any component, with `entry` quoting the line as written, without its line ending.
   - `component_overlap` refuses two components with the same folder or one folder inside another, with `components` listing both as `{ name, folder }` in declaration order.
   - `component_dependency_unknown` refuses a `Depends on` name that is neither a declared component nor the root component, with `component` and `dependency`.
   - `component_cycle` refuses `Depends on` entries that form a cycle, with `cycle` listing its names in dependency order, starting and ending with the cycle's first component in declaration order, each name followed by one it depends on.
10. When a declaration has several problems, the refusal reports the first one in the order of the list above, and within one kind the first in declaration order.
11. The `accept_design` operation takes an optional `component`, a component name, and an accepted design records it on the slice, so that `get_initiative` returns it as the slice's `component` in `record.slices`; a new accepted design replaces it, and a slice accepted before components existed has no `component` field.
12. In a repository that declares no components, an `accept_design` without `component` records the root component's name, and one that names any other component is refused as in clause 13.
13. In a repository that declares components, an `accept_design` without `component`, or with a name that is neither a declared component nor the root component, is refused with `component_unknown`, holding `slice`, `component` as given or `null`, and `components`, every component name with the root component first and then the declared ones in declaration order.
14. An `accept_design` is refused with `component_boundary`, holding `slice`, `component`, and `paths`, each crossing path once in sorted order, when a path in the slice's `slice.md` **Changes** or one of its frozen tests belongs to another component by clause 8 and lies under no shared path; paths under `.prism`, under the configured plans folder, and the roadmap record and projection belong to no component and are not checked.
15. A design proposal whose planned slices record different components of one repository is accepted, and `propose_design` checks clauses 9-14 when it is recorded, so a proposal that `accept_proposal` would refuse for them is refused before it is recorded, and any refused slice refuses the whole proposal.
16. `verify_slice` for a slice that records a component runs that component's `Test command` in the component's folder, or, when the component declares none, the repository's `Test command` in the project root; the root component always runs the repository's `Test command` in the project root; a slice without a component runs the repository's `Test command` in the project root as before and reads no components.
17. A `verify_slice` result that names a `command` also names its working `folder`, project-relative and `""` for the project root, and for a slice with a component its `component`; the recorded run holds `command`, `folder`, and `component` too, and the brief tool result of a finished run keeps `component`, `folder`, and `boundary`.
18. `verify_slice` refuses before it asks for approval: with `component_unknown` as in clause 13 when the slice's recorded component is not a component of the repository now, with `test_command_missing` and `component` when neither the component nor `## Stack` gives a test command, and with `component_folder_missing`, holding `component` and `folder`, when the working folder does not exist or is not a folder.
19. Prism asks the user to allow each distinct pair of test command and working folder once before it first runs it, through the same approval gate, browser answer, and chat approval as today; an approval of a command in one folder does not allow it in another, an approval given before components existed still allows that command in the project root, and the approval question names the command and the folder it runs in.
20. Starting a slice that records a component with `set_status` `in-progress` records the project's content at that moment, after its frozen tests are in place, as the slice's start content; a work tree that Git cannot hash records none, and the start still succeeds.
21. Before it runs the command, `verify_slice` compares the project's content, hashed as a run hashes it, with the slice's start content: every path added, changed, or removed since the start, committed or not, where a rename counts both paths, is a changed path, except the frozen tests of the initiative's other unfinished slices; a changed path that belongs to another component by clause 8 and lies under no shared path crosses the component.
22. A run with a crossing path does not run the command, is recorded as failed with reason `component_boundary`, `crossing` listing at most 200 crossing paths in sorted order, and `crossingCount`, and its result has `status` `failed` with the same reason, message, `crossing`, and `crossingCount`, so the slice cannot complete.
23. A run result and recorded run of a slice with a component hold `boundary`: `checked` when the run compared its content with the start content, and `unchecked` when the slice has no start content, which runs the command without the boundary check.
24. A fit scope is a slice whose design accepted a slice plan, which is a split slice without split evidence, or a leaf whose parent is null or has split evidence; its leaves are its planned slices, or the leaf itself.
25. `verify_slice` with `dependents: true` and `slice` naming a fit scope runs the scope's dependents' run; it refuses with `validation_failed` together with `contractDefects` or for a slice that is not a fit scope, and otherwise with `scope_unfinished`, holding `waiting`, the scope's leaves that are not done in slug order, while a leaf is not done.
26. The dependents of a fit scope are every component that depends, directly or through other components, on a component that one of the scope's leaves records, including the scope's own components; a leaf without a component adds none, and a change under a shared path adds none; a scope without dependents returns `status` `no_dependents`, `scope`, and an empty `components`, and records nothing.
27. Each dependent runs the command and working folder of clause 16, each distinct pair of command and folder runs once, the pairs run in dependency order with the first dependent of each pair deciding its place and ties in declaration order, and clause 18's refusals apply to each dependent, naming the first one in that order.
28. Before the dependents' run starts, one approval gate lists every pair not yet allowed, and the result is `approval_needed` with `gateId`, `scope`, and `commands`, each `{ command, folder, components }`; allowing the gate allows each listed pair as clause 19 does, declining it marks the components of every listed pair `declined` for this run while the allowed pairs still run, and an answer with only a note returns `approval_unclear` as for a slice.
29. The dependents' run is recorded on the scope as a run of kind `dependents`, and its result has `status` `passed` when every dependent passed and `failed` otherwise, `scope`, `components` in run order as `{ name, folder, command, status }` with `status` `passed`, `failed`, or `declined`, `blocked` naming each failed or declined component, and `run`; a run whose commands change project files fails with reason `tracked_files_changed` and blocks every dependent.
30. `get_initiative` returns `dependents`, keyed by scope, for each scope with a recorded dependents' run, holding the latest run's `status`, `passed` or `blocked`, `run`, `finishedAt`, and `blocked`, and it reads no components to do so.
31. The `update_roadmap` `ship` operation refuses with `dependents_blocked`, holding `scopes`, each `{ scope, blocked, reason }` with `reason` `failed` or `not_run`, while a fit scope of the initiative has dependents by the current declaration whose latest dependents' run did not pass or did not run every one of them, and a later passing run of those dependents lets it ship; an initiative in a repository that declares no components ships as before.
32. Every record operation of a checkout whose configuration names a record store but no `Repository` is refused with `repository_name_missing`, holding `proposed`, a name the store would accept for this checkout, chosen as the former warning chose it, and a message that shows the `- Repository: <proposed>` line to add under `## Workspace`; the refusal writes nothing to the store, and the review browser shows the store as unavailable with that message.
33. A checkout whose configuration names no record store serves record operations without a repository name, and a `Repository` line without a `Store` line stays ignored.
34. The review browser shows a slice that records a component with a label `<span class="component-chip" data-component="<name>">` holding the name, in the initiative page's slice tree and board card and on the slice page, and shows no such label for a slice without a component.

## Assumptions

- Probed: today's configuration reader flattens the nested list items of a section into one label map, so clause 1 needs a reader of its own for `## Components` (the parent's `node docs/plans/components/probes/config-nesting.mjs`, observed one map in which the second component's entries replace the first's).
- Probed: Lumen runs each package's tests from the package folder, and 23 packages have a `bunfig.toml` whose preload paths are relative to that folder, so clause 16 runs a component's own command in its folder (the parent's `lumen-components.mjs` probe and Lumen's `packages/di/bunfig.toml`).
- Probed: `git diff-tree -r --no-renames --name-status` between two content trees that verification already hashes lists committed and uncommitted changes alike, lists a moved file as a removal and an addition, and lists nothing under `.prism` or the plans folder (`node docs/plans/components/component-slices/probes/changed-paths.mjs`, observed `M packages/billing/a.ts`, `A packages/billing/moved.ts`, `M packages/shared/b.ts`, `D packages/shared/old.ts`, and no `.prism/workflow.md` or `docs/plans` line), so clause 21 measures changed paths without a new snapshot format.
- Probed: spawning a shell command in a folder that does not exist fails with `spawn /bin/sh ENOENT`, which names the shell rather than the folder (`node docs/plans/components/component-slices/probes/missing-folder.mjs`, observed `{"event":"error","code":"ENOENT","message":"spawn /bin/sh ENOENT"}`), so clause 18 checks the folder first and names it.
- Probed: today's approval of a test command is keyed by the project root and the command text, so keying a pair by its working folder and command keeps every existing approval valid for the project root (`src/server/workflow/verification.mjs`, `approval`, observed the key `sha256("<root>\n<command>")`), which clause 19 relies on.
- Probed: in Lumen, `messages` has 30 transitive dependents among 57 packages and the dependencies form no cycle (the parent's `lumen-components.mjs` probe), so a dependents' run of a scope that changes it runs up to 30 pairs and asks about them in one gate (clause 28) rather than 30.
- Probed: six test files and the host smoke script configure a store without a `Repository` line, and six tests of repository names and machine checkouts build unnamed checkouts on purpose, so clause 32 changes their fixtures and turns those tests into refusals (`grep -ln "Store:" test/server/*.mjs scripts/host-smoke.mjs`, observed `code-links`, `external-record-store`, `prism-call-target`, `record-store-sync`, `remote-record-store`, and `slice-claims` with no `Repository` line, and `grep -n "^test(" test/server/repository-names*.test.mjs test/server/machine-checkouts.test.mjs`, observed the unnamed-checkout tests in `repository-names`, `repository-names-review`, `repository-names-correctness-review`, and `machine-checkouts`).
- Unprobed: a test command that starts background processes which outlive it in the component's folder; the run ends when the command's process group ends, as today, and the commands' changes to project files fail the run with `tracked_files_changed` (clause 29).
