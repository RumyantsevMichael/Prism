# Components for slices and verification

## Outcome

A repository declares its components, each planned leaf slice records one and stays inside it, verification runs its component's tests and the dependents' tests when a scope finishes, the review browser labels each slice's component, and a checkout that names a store but no repository is refused.

## Contract

The parent's accepted split fixes the component model in its Interfaces, and clauses 1-10 restate its clauses 1-10, while Michael's design gate answer of 4 November 2026 extends them: clauses 1, 5, 9, and 11 add a workspace-wide identity `<repository>/<component>` and dependencies on another repository's components, which clauses 36-39 settle, and clauses 40-42 add a declaration proposed from workspace manifests.
Its clause 12 stays true here, because no slice of this contract changes a native index.
The four product defaults of the parent apply: a verified change outside the component fails the run, the dependents' run covers every transitive dependent once per finished scope, it also runs for a scope inside one component, and a change under a shared path makes no component's dependents run.

1. A repository declares components under `## Components` in its committed `.prism/workflow.md` as top-level list items `- <name>: <folder>`, each optionally followed by more-indented list items `- Test command: <command>` and `- Depends on: <dependency>, <dependency>`, where a dependency is a bare component name of the same repository or `<repository>/<component>`; the labels `Test command`, `Depends on`, and `Shared paths` match without case and without a parenthesized note, as other sections' labels do, while a component name is read as written, and lines that are not list items are ignored.
2. A component name matches `^[a-z0-9](?:[a-z0-9_-]{0,62}[a-z0-9])?$`, the rule for repository names.
3. A folder is a project-relative path with forward slashes, read without a trailing `/`, and never empty, `.`, absolute, or holding a backslash, a colon, or an empty, `.`, or `..` segment; a declared folder that does not exist yet is accepted, so a design can declare the component that its slices create, and clause 18 checks where an existing folder leads through symbolic links.
4. A top-level item `- Shared paths: <path>, <path>` under `## Components` lists project-relative files or folders under the same path rules, and a file lies under a shared path when it equals that path or lies inside it.
5. The repository's name is its `Repository` name under `## Workspace`, with or without a record store, and `root` when the configuration gives none, and the root component is named after the repository.
6. The root component holds every file outside all declared folders, tests with the repository's `Test command` under `## Stack`, and depends on nothing, while a declared component may name it under `Depends on`.
7. A repository whose configuration lists no component under `## Components` declares no components and is one component, its root component, holding every file.
8. A file belongs to the declared component whose folder it lies inside, and otherwise to the root component; shared paths never change which component a file belongs to, only which files a slice may change.
9. Every operation that reads a repository's components refuses an invalid declaration with an error whose `code` and fields are listed below, which a tool call returns as a JSON-RPC error whose `data` holds the same `code` and fields; the operations that read components are `update_initiative` with an `accept_design` operation, directly, inside `propose_design`, or replayed by `accept_proposal`, `verify_slice` for a slice that records a component or with `dependents`, and the `update_roadmap` `ship` operation, `get_roadmap` and the review browser read components only for clauses 35, 40, and 41 and are never refused for them, and every other operation, such as `get_initiative`, reads no components and is unaffected.
   - `component_invalid` refuses an entry with an invalid name or folder, an invalid shared path, a name declared twice or equal to the root component's name, an unknown nested label, a nested item before any component, a `Depends on` entry that is neither a valid name nor `<valid name>/<valid name>`, or an invalid `Repository` name without a store, with `entry` quoting the line as written, without its line ending.
   - `component_overlap` refuses two components with the same folder or one folder inside another, with `components` listing both as `{ name, folder }` in declaration order.
   - `component_dependency_unknown` refuses a bare `Depends on` name, or one qualified with the repository's own name, that is neither a declared component nor the root component, with `component` and `dependency` as written.
   - `component_cycle` refuses `Depends on` entries that form a cycle, with `cycle` listing its names in dependency order, starting and ending with the cycle's first component in declaration order, each name followed by one it depends on.
10. When a declaration has several problems, the refusal reports the first one in the order of the list above, and within one kind the first in declaration order.
11. The `accept_design` operation takes an optional `component`, a component name of the repository, bare or as `<repository>/<component>`, and an accepted design records it on the slice as `<repository>/<component>`, so that `get_initiative` returns that identity as the slice's `component` in `record.slices`; a new accepted design replaces it, and a slice accepted before components existed has no `component` field.
12. In a repository that declares no components, an `accept_design` without `component` records the root component, and one that names any other component is refused as in clause 13.
13. In a repository that declares components, an `accept_design` without `component`, or with a name that is neither a declared component nor the root component of this repository, including any name qualified with another repository, is refused with `component_unknown`, holding `slice`, `component` as given or `null`, and `components`, every component's identity with the root component first and then the declared ones in declaration order.
14. An `accept_design` is refused with `component_boundary`, holding `slice`, `component`, and `paths`, each crossing path once in sorted order, when a path in the slice's `slice.md` **Changes** or one of its frozen tests belongs to another component by clause 8 and lies under no shared path; paths under `.prism`, under the configured plans folder, and the roadmap record and projection belong to no component and are not checked.
15. A design proposal whose planned slices record different components of one repository is accepted, and `propose_design` checks clauses 9-14 when it is recorded, so a proposal that `accept_proposal` would refuse for them is refused before it is recorded, and any refused slice refuses the whole proposal.
16. `verify_slice` for a slice that records a component runs that component's `Test command` in the component's folder, or, when the component declares none, the repository's `Test command` in the project root; the root component always runs the repository's `Test command` in the project root; a slice without a component runs the repository's `Test command` in the project root as before and reads no components.
17. A `verify_slice` result that names a `command` also names its working `folder`, the folder the command runs in after symbolic links are followed, project-relative and `""` for the project root, and for a slice with a component its `component`; the recorded run holds `command`, `folder`, and `component` too, and the brief tool result of a finished run keeps `component`, `folder`, and `boundary`.
18. `verify_slice` refuses before it asks for approval: with `component_unknown` as in clause 13 when the slice's recorded component is not a component of the repository now, with `test_command_missing` and `component` when neither the component nor `## Stack` gives a test command, with `component_folder_missing`, holding `component` and `folder`, when the working folder does not exist or is not a folder, and with `component_folder_outside`, holding `component` and the declared `folder`, when the working folder, after symbolic links are followed, is neither the project root nor inside it.
19. Prism asks the user to allow each distinct pair of test command and working folder once before it first runs it, through the same approval gate, browser answer, and chat approval as today; an approval of a command in one folder does not allow it in another, an approval given before components existed still allows that command in the project root, and the approval question, in the review browser and in a cloud session's chat approval message alike, names the command and the folder it runs in, project-relative, and no absolute path.
20. Starting a slice that records a component and has no start content with `set_status` `in-progress` records the project's content at that moment, after its frozen tests are in place, as the slice's start content, together with that time and, when the `## Components` declaration in force is valid and holds the slice's component, that declaration, namely the component's folder, the shared paths, and the other components' folders, while an invalid declaration or one without the slice's component records the start content without a declaration and the start still succeeds; Prism keeps the start content under the local ref `refs/prism/<initiative>/<slice>/<checkout>/start`, where `<checkout>` is the first 16 lowercase hexadecimal digits of the SHA-256 of the project root's real path, which it never pushes, so that `git gc` in any worktree of the repository keeps it, and Prism sets and deletes only the refs of its own `<checkout>`, so linked worktrees and projects that share one Git repository never move or delete each other's refs; a slice keeps its start content when it is restarted after being blocked and when it receives a new design, and setting it back to `not-started` drops its start content and deletes its refs under `refs/prism/<initiative>/<slice>/<checkout>/`, so starting it again records new start content; a work tree that Git cannot hash records none, and the start still succeeds.
21. Before it runs the command, `verify_slice` compares the project's content, hashed as a run hashes it, with the slice's start content: every project-relative path added, changed, or removed since the start, committed or not, where a rename counts both paths, is a changed path, except a frozen test of another slice of the initiative that holds its frozen content, or is absent while that slice is not started, and except a path that the latest passing run of another slice of the initiative changed, when that run finished after this slice's start content was recorded, the path differs between that slice's start content and the content its run tested, and the path now holds the content that run tested, absence included; Prism keeps the content a slice's latest passing run tested under the local ref `refs/prism/<initiative>/<slice>/<checkout>/passed` of clause 20 while the slice has start content, and an exception whose contents Git cannot read, including a recorded tree that is not 40 or 64 lowercase hexadecimal digits, does not apply, and no recorded tree reaches Git as an option; a changed path crosses the component when, by the declaration recorded with the start content, it lies under no shared path and either outside the folder of the slice's declared component or, for the root component, inside another component's folder; so another slice's verified work done while this slice was blocked or waiting does not count, a change of this slice still counts unless another slice's passing run changed that path to the same content, which a change made before that slice started never is, and a changed declaration applies only to slices started after it.
22. A run with a crossing path does not run the command, is recorded as failed with reason `component_boundary`, `crossing` listing at most 200 crossing paths in sorted order, and `crossingCount`, and its result has `status` `failed` with the same reason, message, `crossing`, and `crossingCount`, so the slice cannot complete.
23. A run result and recorded run of a slice with a component hold `boundary`: `checked` when the run compared its content with the start content, and `unchecked` otherwise, and only a slice without start content runs the command `unchecked`; a run of a slice whose recorded start content Git can no longer read, or whose start content was recorded without a declaration by clause 20, does not run the command and is recorded as failed with reason `start_content_missing`, and its result has `status` `failed`, that reason, and a message telling the user to set the slice back to `not-started` and start it again, which records the current content, the slice's earlier changes included, as new start content, and, for start content without a declaration, to make the `## Components` declaration valid and hold the slice's component before starting it again; clause 18's refusals and clause 9's refusal of an invalid declaration come first.
24. A fit scope is a slice whose design accepted a slice plan, which is a split slice without split evidence, or a leaf whose parent is null or has split evidence; its leaves are its planned slices, or the leaf itself.
25. `verify_slice` with `dependents: true` and `slice` naming a fit scope runs the scope's dependents' run; it refuses with `validation_failed` together with `contractDefects` or for a slice that is not a fit scope, and otherwise with `scope_unfinished`, holding `waiting`, the scope's leaves that are not done in slug order, while a leaf is not done.
26. The dependents of a fit scope are every component of the repository that depends, directly or through other components of the repository, on a component that one of the scope's leaves records, including the scope's own components; a leaf without a component adds none, and a change under a shared path adds none; a scope without dependents returns `status` `no_dependents`, `scope`, and an empty `components`, and records nothing.
27. Each dependent runs the command and working folder of clause 16, each distinct pair of command and folder runs once, the pairs run in dependency order with the first dependent of each pair deciding its place and ties in declaration order, and clause 18's refusals apply to each dependent, naming the first one in that order.
28. Before the dependents' run starts, one approval gate lists every pair not yet allowed, and the result is `approval_needed` with `gateId`, `scope`, and `commands`, each `{ command, folder, components }`; allowing the gate allows each listed pair as clause 19 does, declining it marks the components of every listed pair `declined` for this run while the allowed pairs still run, and an answer with only a note returns `approval_unclear` as for a slice.
29. The dependents' run is recorded on the scope as a run of kind `dependents`, and its result has `status` `passed` when every dependent passed and `failed` otherwise, `scope`, `components` in run order as `{ name, folder, command, status }` with `status` `passed`, `failed`, or `declined`, `blocked` naming each failed or declined component, and `run`; a run whose commands change project files fails with reason `tracked_files_changed` and blocks every dependent.
30. `get_initiative` returns `dependents`, keyed by scope, for each scope with a recorded dependents' run, holding the latest run's `status`, `passed` or `blocked`, `run`, `finishedAt`, and `blocked`, and it reads no components to do so.
31. The `update_roadmap` `ship` operation refuses with `dependents_blocked`, holding `scopes`, each `{ scope, blocked, reason }` with `reason` `failed` or `not_run`, while a fit scope of the initiative has dependents by the current declaration whose latest dependents' run did not pass or did not run every one of them, and a later passing run of those dependents lets it ship; an initiative in a repository that declares no components ships as before.
32. Every record operation of a checkout whose configuration names a record store but no `Repository` is refused with `repository_name_missing`, holding `proposed`, a name the store would accept for this checkout, chosen as the former warning chose it, and a message that shows the `- Repository: <proposed>` line to add under `## Workspace`; the refusal writes nothing to the store, and the review browser shows the store as unavailable with that message.
33. A checkout whose configuration names no record store serves record operations without a repository name, and record operations still ignore a `Repository` line without a `Store` line, which only names the repository's components by clause 5.
34. The review browser shows a slice that records a component with a label `<span class="component-chip" data-component="<repository>/<component>">` holding that identity, in the initiative page's slice tree and board card and on the slice page, and shows no such label for a slice without a component.
35. `get_roadmap` reports `readyToShip` `false` for an initiative whose `ship` would refuse with `dependents_blocked`, with a `diagnostics` entry `{ code: "dependents_blocked", message, scopes }` whose `scopes` equal the refusal's, and for an initiative of a repository whose declaration is invalid, with a `diagnostics` entry holding the declaration's refusal `code` and message, without refusing the read; `ship` of an initiative with a leaf that is not done still refuses with `gate_blocked` first, and the review browser's ready to ship label and attention entry, which follow `readyToShip`, appear only once `ship` would succeed.
36. Every component is identified across the workspace as `<repository>/<component>`, with the repository's name of clause 5, so the root component of a repository named `api` is `api/api` and that of a repository without a name is `root/root`; declarations keep bare names, and the refusals of clauses 9 and 10 quote names as written, while every other output that names a component, including `get_initiative`, `component_unknown`, `component_boundary`, `verify_slice` results and runs, the dependents' run, `dependents`, `dependents_blocked`, `get_roadmap`, and the review browser, names it by that identity.
37. A `Depends on` entry `<repository>/<component>` naming another repository is recorded as written and checked only for the name rule of each part; it is never refused as unknown, takes no part in a cycle, and makes no test command of the other repository run.
38. A `Repository` line under `## Workspace` of a configuration without a record store names the repository when it follows the name rule of clause 2, and makes every operation that reads components refuse with `component_invalid`, quoting it, when it does not.
39. The dependents' run covers only the scope's own repository: it reads no other repository's configuration and no list of this machine's checkouts, a dependency on another repository's component makes nothing run and is not reported, and its result and recorded run hold no field about other repositories.
40. `get_roadmap` returns `components` with the repository's `repository` name and `declared`, the root component and then each declared component in declaration order as `{ component, folder, testCommand, dependsOn }`, where the root component's `folder` is `""` and its `testCommand` the repository's `Test command`, a declared component's `testCommand` is the command it declares, `testCommand` is `null` when there is none, and `dependsOn` lists identities in the order declared; for an invalid declaration `declared` is empty and `problem` holds the refusal's `code` and `message`.
41. When the configuration lists no component under `## Components` and a workspace manifest at the project root gives workspace patterns, `components.proposal` holds `markdown`, the `## Components` block in the form of clause 1 ready to commit, with one line per component, then its `Test command` and `Depends on` lines when it has them, a final `Shared paths` line when there are any, and every line ending with a newline, and its `components`, each `{ name, folder, testCommand, dependsOn }` in folder order, `sharedPaths`, `skipped`, each manifest Prism could not read as `{ path, reason }`, and `problem` when the proposed block would be refused, as `{ code, message }`; the patterns come from `workspaces` in `package.json`, as an array or as `packages` of an object, `packages` in `pnpm-workspace.yaml`, `members` and `exclude` of `[workspace]` in `Cargo.toml`, and the `use` directives of `go.work`, where `*` matches within one folder name, `**` matches any number of folders, and a pattern starting with `!` or listed in `exclude` removes folders; every folder a pattern matches that holds a `package.json`, `Cargo.toml`, `go.mod`, or `Package.swift` is proposed once, except one with a `node_modules` segment or a segment starting with `.`; a member manifest Prism cannot read is listed in `skipped` while its folder is still proposed under its folder name, without a test command or dependencies; the proposal is absent when the configuration declares components or no manifest gives patterns, and Prism never writes it to any file.
42. A proposed component is named after its folder's `package.json` `name` after the last `/`, else its `Cargo.toml` `[package]` `name`, else the last segment of its `go.mod` module, else its folder's last segment, lowercased, with each run of other characters than `a-z`, `0-9`, `_`, and `-` replaced by `-`, trimmed of leading and trailing `-` and `_`, and cut to 64 characters, and a name that ends up empty, equal to the root component's name, or already taken uses the folder's last segment the same way, then adds `-2`, `-3`, and so on; the project's package manager is the first that applies of `bun` when the project root holds `bun.lock` or `bun.lockb`, `pnpm` when it holds `pnpm-lock.yaml` or `pnpm-workspace.yaml`, `yarn` when it holds `yarn.lock`, and `npm` otherwise, whichever root manifest gave the patterns and whether or not `package-lock.json` exists, where a root file counts only when it is a regular file, not a folder or a symbolic link; its `testCommand` is `<manager> run test` with that package manager when its `package.json` has a `test` script, and `null` otherwise; its `dependsOn` names, in name order, every other proposed component whose `package.json` name is a key of its `dependencies`, `devDependencies`, `peerDependencies`, or `optionalDependencies`, whose folder a `path` of its `Cargo.toml` `[dependencies]` or `[dev-dependencies]` resolves to, or whose `go.mod` module its `go.mod` requires, where a `package.json` name or `go.mod` module that several proposed components share stands only for the first of them in folder order, and a folder with a manifest listed in `skipped` has no name or module to match; `sharedPaths` lists, in the order `bun.lock`, `bun.lockb`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `Cargo.lock`, `go.work.sum`, each of them that exists at the project root and belongs to a workspace tool whose root manifest gives patterns by clause 41: the package manager's own lockfiles, which are `bun.lock` and `bun.lockb` for `bun`, `pnpm-lock.yaml` for `pnpm`, `yarn.lock` for `yarn`, and `package-lock.json` for `npm`, when `package.json` or `pnpm-workspace.yaml` gives patterns, `Cargo.lock` when `Cargo.toml` does, and `go.work.sum` when `go.work` does, so a lockfile of another package manager or of a tool whose manifest gives no patterns stays in the root component.

## Assumptions

- Probed: today's configuration reader flattens the nested list items of a section into one label map, so clause 1 needs a reader of its own for `## Components` (the parent's `node docs/plans/components/probes/config-nesting.mjs`, observed one map in which the second component's entries replace the first's).
- Probed: a private Bun monorepo runs each package's tests from the package folder, and many packages have a `bunfig.toml` whose preload paths are relative to that folder, so clause 16 runs a component's own command in its folder (the parent's `workspace-components.mjs` probe and one package's `bunfig.toml`).
- Probed: `git diff-tree -r --no-renames --name-status` between two content trees that verification already hashes lists committed and uncommitted changes alike, lists a moved file as a removal and an addition, and lists nothing under `.prism` or the plans folder (`node docs/plans/components/component-slices/probes/changed-paths.mjs`, observed `M packages/billing/a.ts`, `A packages/billing/moved.ts`, `M packages/shared/b.ts`, `D packages/shared/old.ts`, and no `.prism/workflow.md` or `docs/plans` line), so clause 21 measures changed paths without a new snapshot format.
- Probed: a content tree that no ref reaches is gone after `git gc --prune=now`, one that a ref under `refs/prism/` names survives it, and neither a push of every branch nor a clone carries that ref (`node docs/plans/components/component-slices/probes/start-content-ref.mjs`, observed `{"withRef":true,"withoutRef":false,"remoteRefs":["refs/heads/main"],"clonedPrismRefs":[]}`), so clauses 20 and 21 keep start content and passing contents readable with local refs.
- Probed: linked worktrees share every ref under `refs/prism/`, so a delete in one removes the other's; a ref under `refs/worktree/` is each worktree's own, but `git gc --prune=now` in another worktree prunes what it names and then fails on it; two clean worktrees at one commit hash the same content tree, so a ref named by its tree cannot tell their start contents apart; and refs named by each project root's real path survive `git gc` in either worktree while each worktree deletes only its own, and a plain push or clone carries none of them, while a mirror push, a mirror clone, and a bundle of every ref carry them (`node docs/plans/components/component-slices/probes/worktree-refs.mjs`, Git 2.43.0, observed `{"sameContent":true,"shared":{"mainRefsAfterLinkedDelete":[]},"perWorktree":{"gcInMain":"ok","linkedTreeAfterGcInMain":false,"gcInLinked":"fatal: bad object refs/worktree/prism/work/s/start"},"byCheckout":{"refs":2,"gcInLinked":"ok","gcInMain":"ok","mainTree":true,"linkedTree":true},"carried":{"pushAll":false,"clone":false,"pushMirror":true,"cloneMirror":true,"bundleAll":true}}`), so clause 20 names each ref by its checkout.
- Probed: Git records a committed symbolic link as a link, so the folder rules of clause 3 see only its text, while following it can lead outside the project or to another folder inside it (`node docs/plans/components/component-slices/probes/linked-folder.mjs`, observed `{"out":{"inside":false},"in":{"inside":true,"relative":"packages/shared"},"tracked":["120000 vendor/in","120000 vendor/out"]}`), so clause 18 checks the followed folder and clauses 17 and 19 name it.
- Unprobed: a slice resumed in another checkout that shares the records but not the Git objects, or another slice's unverified work left in the shared work tree; the first fails with `start_content_missing` by clause 23 and the second with `component_boundary`, never a silent pass.
- Probed: spawning a shell command in a folder that does not exist fails with `spawn /bin/sh ENOENT`, which names the shell rather than the folder (`node docs/plans/components/component-slices/probes/missing-folder.mjs`, observed `{"event":"error","code":"ENOENT","message":"spawn /bin/sh ENOENT"}`), so clause 18 checks the folder first and names it.
- Probed: today's approval of a test command is keyed by the project root and the command text, so keying a pair by its working folder and command keeps every existing approval valid for the project root (`src/server/workflow/verification.mjs`, `approval`, observed the key `sha256("<root>\n<command>")`), which clause 19 relies on.
- Probed: in that monorepo, the most depended-on package has dozens of transitive dependents and the dependencies form no cycle (the parent's `workspace-components.mjs` probe), so a dependents' run of a scope that changes it runs dozens of pairs and asks about them in one gate (clause 28) rather than one gate each.
- Probed: six test files and the host smoke script configure a store without a `Repository` line, and six tests of repository names and machine checkouts build unnamed checkouts on purpose, so clause 32 changes their fixtures and turns those tests into refusals (`grep -ln "Store:" test/server/*.mjs scripts/host-smoke.mjs`, observed `code-links`, `external-record-store`, `prism-call-target`, `record-store-sync`, `remote-record-store`, and `slice-claims` with no `Repository` line, and `grep -n "^test(" test/server/repository-names*.test.mjs test/server/machine-checkouts.test.mjs`, observed the unnamed-checkout tests in `repository-names`, `repository-names-review`, `repository-names-correctness-review`, and `machine-checkouts`).
- Probed: that monorepo's root `package.json` gives the one workspace pattern `packages/*`, whose matched folders mostly hold a `package.json`, while a few hold only a `Cargo.toml` whose `[package]` `name` equals the folder or only a `Package.swift`, and its root holds `bun.lock` and no other lockfile (`node docs/plans/components/component-slices/probes/workspace-manifests.mjs <monorepo checkout>`, observed `patterns: ["packages/*"]`, all three manifest kinds under `firstManifest`, and `lockfiles: ["bun.lock"]`), so clause 41 proposes every matched folder that holds one of the four manifests, which covers every folder rather than only those with a `package.json`, and the Rust and Swift packages get no test command from a script.
- Unprobed: TOML and YAML beyond inline arrays, inline tables, and block lists of plain strings; clause 41 lists a manifest Prism cannot read under `skipped` with the reason instead of guessing.
- Unprobed: a test command that starts background processes which outlive it in the component's folder; the run ends when the command's process group ends, as today, and the commands' changes to project files fail the run with `tracked_files_changed` (clause 29).
