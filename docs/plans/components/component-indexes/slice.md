# Native indexes per component

## Outcome

Prism prepares a native index per component, only for the components a tool needs, keeps the others after a failure, and answers path-scoped queries from matching components and unscoped semantic queries from every prepared one, naming those it left out.

## Contract

The component model is the one `component-slices` delivered: its clauses 1-10 and 36 fix the declaration, the root component, which component a file belongs to, the identity `<repository>/<component>`, and the refusals of an invalid declaration.
This contract replaces the parent's interface clause 12, which kept one whole-repository index until this part.
The native index tools are `search_repository_concepts`, `find_shared_dependencies`, `report_module_interfaces`, `find_shared_literals`, `report_cohesion_clusters`, `find_same_name_units`, `report_complex_units`, and `plan_repository_context` with provider `auto` or `native`; the status tools are `get_repository_intelligence_status`, `discover_repository_intelligence`, and the `native` field of `list_repository_intelligence_providers`.
The component order is the root component first and then the declared components in declaration order.
Documents outside every declared folder stay in the root component's index, as Michael decided ("keep docs as is").

### A repository without components

1. In a repository whose configuration lists no component under `## Components`, the native index tools, the status tools, background preparation, the review browser's index status, rebuild, and code places, and retained baseline analyses work as before this contract: one index of the whole repository in the same storage, so an index prepared before this contract is reused, with the same results and no `components` field (`components.md§23`).

### Component indexes

2. In a repository that declares components, Prism prepares a separate native index for each component, holding exactly the source files of the native scan that belong to that component, under their project-relative paths, and the native limits of 20,000 files, 64 MiB of source, a 512 MiB index file, and 30 minutes of preparation apply to each component's index on its own (`components.md§20`).
3. A component's content is the project-relative path and SHA-256 of each source file it holds, computed the same way for the live project and for a retained baseline, and a component's index is up to date when it was built from the component's current content, so a change to another component's files never makes it out of date.
4. Each component's index lives in its own storage, keyed by the project's real path and the component's name, so it is reused across sessions, after another component changes, and after the repository's name changes; a new index of a component reuses the embeddings of unchanged fragments from that component's previous index, and Prism keeps each component's current index and at most four earlier ones, counted per component.
5. A server process prepares one index at a time; a call queues, in component order, each component it needs whose index is missing or out of date and that is not already waiting or preparing, moves each component it needs that is already waiting ahead of every waiting component that it does not need, keeping component order among them, never interrupts the running preparation, and never prepares a component it does not need (`components.md§21`).
6. A call waits at most its existing bound in total for the preparations of the components it needs, 10 seconds for a tool call, and then answers with the components that are ready.
7. A component's preparation that fails or reaches a native limit publishes nothing for that component, keeps every other component's index and the component's own earlier indexes, and records its failure as `{ code, message }`, where reaching a native limit has `code` `resource_limit` and a message that names the limit; a server process does not prepare a component again for the same content after it reached a native limit, except through the review browser's rebuild of clause 27, while a component that failed otherwise is prepared again by the next call that needs it (`components.md§22`).

### Which components a call reads

8. A native index tool call selects, when it passes `filters.paths`, each component that holds a scanned file equal to or inside one of the paths, and otherwise every component that holds at least one scanned file; `plan_repository_context` always selects every such component (`components.md§24`, `§25`).
9. A call answers only from the indexes of the components it selects, so `filters` still narrow the results as before, while a group of `find_shared_dependencies`, `find_shared_literals`, or `find_same_name_units` keeps only members in the selected components, and `report_module_interfaces` counts only importers in the selected components (`components.md§24`).

### Results from several indexes

10. In a repository that declares components, every result of a native index tool other than `plan_repository_context`, which clause 20 covers, holds `components`, one entry per selected component in component order, `{ component, folder, status, indexRevision, failure }`, where `component` is the identity, `folder` is `""` for the root component, `status` is `included` when its up-to-date index answered, `waiting`, `preparing`, or `failed`, `indexRevision` is that index's revision when it is included and `null` otherwise, and `failure` is the failure of clause 7 when it failed and `null` otherwise.
11. Such a result has `status` `ready` when every selected component is included, also when none is selected, `partial` when some are included and some are not, `preparing` when none is included and at least one is waiting or preparing, and `degraded` when every selected component failed; a `preparing` result holds the empty result lists of today's preparing answer, and `preparationId` is `null`.
12. When a result does not include every selected component, its `diagnostics` start with `{ code: "components_missing", message, components }`, where `components` lists the identities of the components it does not include in component order, and the message names each of them with its status and, for a failed one, its failure message (`components.md§22`, `§26`).
13. Such a result's `snapshot` is the SHA-256 of the lines `<identity> <content fingerprint>\n` of the selected components in component order, where the content fingerprint is the SHA-256 of the lines `<path> <sha256>\n` of the component's content of clause 3, sorted by path in code point order, and its `indexRevision` is the SHA-256 of the lines `<identity> <revision>\n` of the included components in component order, or `null` when none is included; an `expectedSnapshot` that differs from the `snapshot` of the same selection is refused with `stale_snapshot`, as today.

### Semantic search

14. Each `search_repository_concepts` result in a repository that declares components holds `component`, the identity of the component whose file it names.
15. When one selected component is included, the search returns that index's results in that index's order (`components.md§24`).
16. When several selected components are included, each of them answers the query with the call's `filters` and `limit`, and the merged list orders their results by `cosineSimilarity` from highest to lowest, ties in component order and then in each index's order, keeps the first `limit`, and numbers `fusedRank` from 1 in merged order, while `fusedScore` and `lexicalScore` stay as each index computed them (`components.md§25`).
17. When no selected component is included and none is waiting or preparing, the search returns today's lexical fallback over the files of the selected components, each result with `component` and `cosineSimilarity` `null`, and `status` `degraded`.

### Structural reports and context plans

18. The six structural reports run over the included components as over one index that held their units, edges, references, coverage, and file contents, so their ordering, `limit`, `offset`, totals, and `coverage` apply to that union, and they report incomplete structure when any included component's structure is incomplete.
19. Search receipts and analysis receipts in a repository that declares components record the result's `components`, `snapshot`, and `indexRevision`.
20. `plan_repository_context` takes its semantic candidates from the merged search of clause 16 over every selected component and expands the graph within the included components; it returns today's preparing answer while no component is included, and while some component is not included, `diagnostics.provider` holds the `components_missing` diagnostic of clause 12, `diagnostics.estimateEligible` is `false`, and every `tokenEstimate` value is `null`.

### Status

21. In a repository that declares components, the status tools return `components`, one entry per component that holds a scanned file, in component order, `{ component, folder, status, preparationId, snapshot, indexRevision, builtAt, progress, coverage, failure, diagnosticCount }`, where `status` is `unprepared`, `waiting`, `preparing`, `ready`, `indexed`, or `degraded` with today's meanings, `waiting` meaning queued; the top-level `status` is `preparing` when a component is waiting or preparing, else `degraded` when a component's latest preparation in this process failed, else `indexed` when a component has an index, else `unprepared`; the top-level `preparationId`, `snapshot`, `indexRevision`, and `coverage` are `null`, `progress` is the running preparation's progress with `component` added, and `diagnostics` lists every component's diagnostics, each with `component`, paged by `offset` and `limit` as today; the status tools start no preparation, and `waitMs` waits for the running preparation.

### Retained baselines

22. A native index tool call with `snapshotId` splits the retained baseline's source files into components by the current declaration and prepares one index per component from the baseline's content, which reuses a component index built from the same content, live or retained, and clauses 8-18 apply to the baseline.
23. Such a call retains the baseline's analysis only when it selected every component of the baseline and included all of them.
24. The baseline analysis that conservation evidence, change map comparisons, and derived change maps prepare covers every component of the baseline, is `preparing` while one of them is waiting or preparing, and then retains the union of the included components' units, edges, references, coverage, and diagnostics, with the files of a failed component retained without units and as not covered, and with the `components_missing` diagnostic of clause 12.

### Invalid declarations, background preparation, and the review browser

25. In a repository whose `## Components` declaration is invalid, the native index tools and the status tools refuse with the declaration's refusal of the component model's clause 9, as a JSON-RPC error whose `data` holds its `code` and fields, before any preparation, and background preparation and rebuild prepare nothing.
26. Background preparation at server start in a repository that declares components prepares, in component order, each component that has an index in this storage and is out of date, and no other component.
27. The review browser's rebuild, automatic or asked for by the person, prepares each component that has an index or a recorded failed preparation in this storage and is out of date or failed, including one that reached a native limit, and no other component.
28. The review browser's index status in a repository that declares components has `state` `preparing` when any component is preparing in any session, else `failed` or `interrupted` when some component's latest preparation ended so after its latest index, else `ready` when some component has an index, else `none` or `unavailable` as today; `progress` is the running preparation's progress with `component` added, `index` describes the most recently built component index, `stale` is `true` when the Git state recorded with any component's index differs from the current one, `false` when all match, and `null` otherwise, and `components` lists `{ component, state }` for each component with an index or a recorded preparation, in component order.
29. The code places of the review browser's design view come from the published units of every component's latest index, merged, so a file of a component without an index has no places.

## Assumptions

- Probed: an index of only some files of a repository, built in place from a filtered snapshot, holds exactly those files under their project-relative paths (`node docs/plans/components/component-indexes/probes/filtered-index.mjs <monorepo checkout> exclude packages`, observed `filesOutsideSelection: 0` of every file), so clause 2 needs no copy of a component's folder.
- Probed: on the two-package fixture, a unit's `cosineSimilarity` for one query differs by at most 0.0074 between the whole-project index and its package's index, while its `lexicalScore` and rank differ widely, such as 0.88 against 1.63 and rank 1 against 2 for `retryRequest` (`node docs/plans/components/component-indexes/probes/component-merge.mjs <scratch>`), because the embedding model and the query vector are the same and only lexical statistics depend on the corpus, so clause 16 merges by `cosineSimilarity`.
- Probed: unit identifiers are equal in the whole-project index and the package indexes and no identifier occurs in two package indexes (same probe, observed `componentIdsInWhole: 7` of 7 and `idsSharedBetweenComponents: 0`), so clauses 18 and 24 can take the union of component indexes without renaming units.
- Probed: a large private monorepo's root component, every file outside `packages/` with `docs/` as nearly all of it, indexes into about four times the fragments of its largest package, and prepared in about 23 minutes with a 307 MB index file and 1.6 GiB peak memory on this four-core machine, about 19 new embeddings a second (`node docs/plans/components/component-indexes/probes/filtered-index.mjs <monorepo checkout> exclude packages`, observed `ready`, `filesOutsideSelection: 0`), so it fits the 30 minute and 512 MiB limits here with little room, while at the 11 a second of the parent's largest-package probe it would take about 40 minutes and fail with `resource_limit`, which clause 7 isolates and names.
- Probed: in the parent's index of that monorepo's largest package, nearly every file parsed (`syntaxCoverage`), while fewer than one in ten count as structurally covered, because a file counts as covered only when the graph resolves every reference in it; most files have the diagnostic `The graph has unresolved references in this file.`, a few have a real graph SDK extraction failure, and the index's structure is incomplete because the graph's reads outside the package, such as `../../tsconfig.json` and files of sibling packages, were denied (the cached index's `fileCoverage`, `syntaxCoverage`, and `diagnostics`); the fixture shows the same rule in a whole-project index, where `backoff.ts`, which calls only `Math.min`, counts as not covered (`component-merge.mjs`), so the low count is a separate coverage defect that applies with or without components and is not a TypeScript extraction failure, and a component index's reads of other components stay reported as incomplete structure under clause 18, as Michael's default that an index holds no copies of the components it depends on implies.
- Probed: a retained baseline's fingerprint is computed from its canonical file list, not with the live scan's fingerprint (`src/server/conservation/conservation-store.mts`, `capture` and `source`), so today a baseline never reuses a live index, and clause 3 defines a component's content the same way for both so that clause 22 can reuse one.
- Probed: the runtime keys preparation jobs and storage by the project's real path alone and runs its builds one after another in arrival order (`src/server/repository-intelligence/native-semantic-runtime.mts`, `location`, `jobs`, and `sequence`), and a failed job is prepared again by the next call, so clauses 4, 5, and 7 need a key per component, a queue the latest call can reorder, and a remembered limit failure.
- Unprobed: two sessions of one project preparing different components at once; each component's storage has its own lock, as the project's storage has today, so they never write one index, and a session that finds a component locked reports it `preparing`.
- Unprobed: the Git state recorded with each index covers the whole repository, so an edit in one component marks every component's index stale in the review browser's status; the rebuild of clause 27 then reuses every unchanged component's index without building it, which keeps the cost bounded.
