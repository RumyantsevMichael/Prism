# Workspace artifacts in the store

## Outcome

A workspace's descriptive artifacts live in its shared store, scoped to the workspace, a repository, or a component, reviewed in Prism with diffs and comments, and changed in status only at gates, while executable artifacts stay with the code.

## Design questions settled

- Agents read and write store artifacts only through Prism tools, addressed by the project-relative path the checkout's configured paths give them, because writes outside the working folder ask for approval or fail in sandboxed hosts, and only a tool write lets Prism lock, sync, and check status ([store-artifacts ADR](../../ADRs/workflow-records/store-artifacts.md)).
- Configured paths map to fixed kind folders in the store, and a repository's or component's artifacts live in that scope's own folder, so two repositories never share a location, while within what one checkout sees each path names one artifact.
- Concurrent changes to one Markdown artifact merge by Git's line merge, which combines changes to different sentences of a one-sentence-per-line file (probe below), and a line that changed differently on both sides falls back to the whole-file rule that records use.
- Artifact names follow one positive name form instead of a list of dangerous names, so every `.git` variant, Git's short name `git~1`, dotfiles such as `.gitignore`, temporary files, and invisible characters are refused by one rule, at the cost of refusing names with spaces or non-Latin letters.
- The name form also refuses the two kinds of name that Git for Windows refuses to check out while Git elsewhere adds them, a Windows device name before the first `.` and a `.` at the end, because one such name written from Linux or macOS would stop the store on every Windows machine of the workspace (probe below).
- Two paths that differ only in letter case are one file on the default macOS and Windows file systems, so no update creates a path that collides in letter case with one the checkout sees, while a colliding pair that the store already holds stays as it is, so that no bytes are lost before a person removes one.
- Store paths stay short enough for a store's managed clone on Windows to check out without Git's `core.longpaths`, so an artifact's location holds at most 120 characters, refused with a code of its own, `artifact_path_too_long`, rather than `artifact_name_invalid`, because no single name breaks a rule and the remedy is a shorter path or another scope (probe below).
- Agents choose portable names in every project, not only in one with a store, because one repository is often checked out on Windows, macOS, and Linux, and the skills state the rule once as a Common term without saying how Prism stores anything; the guidance asks for a project-relative path of at most 100 characters and identifiers of at most 40, which under the default configured paths keeps a repository-scope location within §16's 120 characters for a repository name of at most 11 characters, while the tools enforce the exact limits.
- Prism names plan folders from initiative and slice slugs, so a slug is checked against the name rules when it is created, before any plan file exists, rather than when Prism first writes into its folder.
- Prism's lock and temporary files stay beside the store files they guard, because the ignore file that Prism writes into a store lists `*.lock` and `.*.tmp`, so the store's Git would leave out an artifact with such a name wherever the locks lived; the name form already refuses `.*.tmp`, which begins with `.`, and only the `.lock` ending is reserved besides, in any letter case because a case-insensitive file system makes `x.LOCK` the lock file of `x` (probe below).
- Code repositories keep their configured paths, which stay the artifacts' addresses, and the move reports each tracked file that still names a moved path, so a person updates the instructions instead of Prism rewriting them.
- A move removes checkout files only right before Prism writes a tool result that reports them, rather than carrying its report in a refusal, because a cancelled call or one answered after the host closed its input has no result that reaches the agent, and one rule then covers refused, cancelled, and closed calls without a removal that no result names.
- Nothing in Prism can stop a cancel or a host close from coming between a move's removal of a checkout file and the result that reports it, so the first tool call of each later session reports as moved earlier every such file whose deletion Git's index still lists and whose store location holds a file, and stops only once a person stages or commits the deletion, because that is the one sign that a person has seen the removal, while the order of the reference scan and the removals, which only narrows that window, is left to the implementation.
- The review browser counts apart the files that a move keeps for good, such as an image in a plan folder, and shows them as a plain note without names, because a warning that a tool call will move them would never clear, while a file that a person has since made text again counts as waiting once more.
- Status changes at gates are recorded beside the artifact in the store ([artifact status ADR](../../ADRs/workflow-records/artifact-status-at-gates.md)).
- An approval answer is the review app's `gate.answer` action on a target `approval:<gate id>`, applied through the same route, origin check, and write session as every other gate answer, and no route of its own remains, because review-app-actions.md§9 accepts a change from the review app only as an action ([review-app-actions ADR](../../ADRs/workflow-records/review-app-actions.md)).
  The action's revision is the artifact's version, so a page that read an older artifact is refused as stale, and the entry is recorded in the artifact's status record, because an approval belongs to no initiative; that recording waits on the person's answer to the proposed amendment of review-app-actions.md§7 in [review-app-actions-amendment.md](review-app-actions-amendment.md) and the partial supersession in the [artifact-status-at-gates ADR](../../ADRs/workflow-records/artifact-status-at-gates.md).

## Contract

### Artifact paths and store layout

1. In a checkout whose `.prism/workflow.md` names a store under `## Workspace`, a project-relative path, with its `.` and `..` components resolved, is an artifact path when it equals the configured `Glossary` or `Roadmap` path or lies inside the configured `Requirements`, `ADRs`, or `Plans` folder, lies inside neither the configured `Feature files` nor `User guide` folder, and has a well-formed name; a path names its kind by the longest configured path that contains it, and a key set to `n/a` names no kind.
   A path has a well-formed name when every component of it below its configured folder, and the file name of the configured `Glossary` or `Roadmap` path, begins with an ASCII letter or digit, holds only ASCII letters, digits, `.`, `_`, and `-`, does not end in `.`, does not end in `.lock` in any letter case, the name of the lock that store sync takes beside a store file, and is no Windows device name, which is a component whose part before its first `.`, or the whole component when it has none, is `con`, `prn`, `aux`, `nul`, `com0` to `com9`, or `lpt0` to `lpt9` in any letter case, such as `aux`, `NUL.txt`, or `Lpt9.tar.gz`; no listing shows a file whose path has no well-formed name.
2. A store holds artifacts under `artifacts/` in scope folders: the workspace scope at `artifacts/`, a repository at `artifacts/repositories/<repository>/`, and a component at `artifacts/repositories/<repository>/components/<component>/`.
   Because repository and component names name store folders, and a repository's name also names its registration file `repositories/<repository>.json`, each is a portable name: Prism already takes only 1 to 64 lowercase ASCII letters, digits, `-`, and `_` that begin and end with a letter or digit, which meets the §1 name form and keeps the registration file within 82 characters and the deepest scope folder within 163 characters below the store's folder, inside the bounds of §3, while §16 bounds each artifact location in a scope, and a name must also be no Windows device name in the §1 sense, `con`, `prn`, `aux`, `nul`, `com0` to `com9`, or `lpt0` to `lpt9`.
   A checkout whose `Repository` name is a Windows device name is refused as an invalid name is, with `repository_name_invalid`, by every record operation and by both artifact tools before Prism registers the name or writes any file, whether or not the store already registers it; `data.proposed` holds a portable name that the store would accept, and a registration that the store already holds under such a name accepts no checkout and keeps no remote from registering under another name.
   A `write` that creates an artifact in a component scope whose component name is a Windows device name, whether its `scope` input or its nearest ancestor folder as §14 decides names that scope, and a `move_scope` into such a scope are refused with `component_name_invalid`, `data.component` holding the name, and a message that asks to rename the component under `## Components` in `.prism/workflow.md` or to choose another scope; a component folder of such a name that the store already holds stays seen, and each of its artifacts is listed, read, written with its version, edited, removed, and moved to another scope by its path.
3. Inside a scope folder an artifact lives at `requirements/<rest>`, `adrs/<rest>`, `plans/<rest>`, or `glossary.md`, where `<rest>` is the artifact path below its configured folder, and the roadmap view lives only at `artifacts/roadmap.md`; the artifact's location is its path below `artifacts/`.
   An artifact's location holds at most 120 characters, and every store path that Prism derives from a location, such as a comment file or a status record, holds at most 186 characters below the store's folder, with each of its folders at most 174.
4. A scope is reported as `{ kind, label }` with `kind` `workspace`, `repository`, or `component`, `repository` and `component` names where they apply, and `label` `workspace`, `<repository>`, or `<repository>/<component>`.
5. A checkout sees the workspace scope, its repository's scope under its accepted `Repository` name, and the scope of every component folder of its repository that the store holds.
6. A path resolves to the one scope the checkout sees that holds it; when more than one does, a read or update without `scope` is refused with `artifact_ambiguous` and `data.scopes` listing their labels, and a `scope` input picks one.
7. A `scope` input is `"workspace"`, `"repository"`, or `"component"` with a `component` name; a component that the checkout's `## Components` does not declare is refused with `component_unknown`, and any other value with `scope_invalid`.

### Reading artifacts

8. `get_artifact` with `path` naming a file returns `path`, `scope`, `kind`, `version` (`sha256:` and the hex SHA-256 of the file's bytes), `bytes`, `totalLines`, `offset`, `content`, and `nextOffset`, which is null on the last page.
9. A read returns the text of whole lines from `offset` (1-based, default 1), with their line endings, up to `limit` lines (default 2000) and at most 64 KiB, and always at least one line, so the pages of a long file joined in order give its text.
   That text is the stored bytes decoded as UTF-8 exactly, a leading byte order mark and every carriage return included, so a `write` of the joined pages stores the same bytes and version, and an `edit` changes only the text it replaces.
10. `get_artifact` without `path`, or with `path` naming a folder, lists every artifact the checkout sees below it as `artifacts` entries of `path`, `scope`, `kind`, `version`, and `bytes`, sorted by path and then scope label, at most 2000 entries with `truncated` true when more exist.
11. A path no seen scope holds is refused with `artifact_not_found`, and a file that is not UTF-8 text with `artifact_not_text`.
   Every artifact is a regular file: a location that holds a symbolic link or a special file such as a pipe or device, or lies below a symbolic link, is never opened or followed, listings leave it out, and every read and operation that names it is refused at once with `invalid_path`.

### Writing artifacts

12. `update_artifact` takes `operations`, at most 50, each one of `write` (`path`, `content`, `expectedVersion`, optional `scope`), `edit` (`path`, `expectedVersion`, `edits` of `oldText` and `newText`), `remove` (`path`, `expectedVersion`), and `move_scope` (`path`, `expectedVersion`, `scope`, optional `component`), and returns `artifacts` with each touched artifact's `path`, `scope`, and new `version`, or `removed` true.
13. `expectedVersion` is the version last read, or null to create; any other mismatch with the store is refused with `version_conflict` and `data.version` holding the current version or null.
   Store sync replaces no artifact file between an update's first version check and its last write, so an upstream change either lands before the update, which is then checked against it, or reaches the store's merge as a change made concurrently with the update, and never vanishes under the update's write.
   An update's changes reach the store's history together: no store commit, local or pushed, holds some of one update's changes without the rest, so another machine sees an update, such as both locations of a `move_scope`, whole or not at all.
14. A created artifact takes the given scope, else the scope of its nearest ancestor folder that one seen scope holds, else the workspace scope, and creating a path that another seen scope already holds is refused with `artifact_exists` and `data.scope`.
   Two artifact paths of one kind collide in letter case when some folder or file of one, taken with the folders above it, equals the same part of the other only when ASCII letter case is ignored, such as `docs/plans/x/Plan.md` and `docs/plans/x/plan.md`, or `docs/plans/X/a.md` and `docs/plans/x/b.md`; a `write` that creates an artifact, and a `move_scope`, whose path collides in letter case with an artifact path that a seen scope holds before the update, or with the path of another `write` of the same update, is refused with `artifact_name_conflict` and `data.path` holding that other path, so a rename that changes only letter case takes two updates, a `remove` and then a `write`.
   A colliding pair that the store already holds, such as one that two machines created before either synced, stays as it is: a listing shows each path, and each is read, written with its version, edited, and removed by its own path.
15. Each `edit` replaces one occurrence of `oldText` that occurs exactly once in the text as earlier edits left it, and is refused with `edit_not_applied` and `data.edit` holding its index otherwise.
16. Content is UTF-8 text of at most 1 MiB, refused with `artifact_too_large` above it.
   A `write` that creates an artifact, and a `move_scope`, whose location in the scope the artifact would take holds more than 120 characters is refused with `artifact_path_too_long`, `data.location` holding that location, `data.limit` 120, and a message that asks for a shorter path or a scope with a shorter folder; a longer artifact that the store already holds stays listed, read, written with its version, edited, and removed by its path.
17. Prism checks every operation of an update before it changes any file, and a refused update changes no file.
   A `write` whose location is a folder that holds artifacts, lies below a file that the store holds, or lies below the location of another `write` of the same update is refused with `invalid_path`, so every location an update writes ends as a regular file.

### Where artifacts are kept

18. Feature files, step definitions, frozen tests, executable contracts, and user documentation are not artifact paths: `get_artifact` and `update_artifact` refuse them, and every other path outside the artifact paths, with `not_an_artifact`, whose message says the file stays in the checkout.
   A path that would be an artifact path but for its name is refused by every read and operation of both tools with `artifact_name_invalid`, whose `data.invalidName` holds the first component that breaks the name form and whose message states the form, an ASCII letter or digit first, then only ASCII letters, digits, `.`, `_`, and `-`, no `.` or `.lock` ending, and no Windows device name, and does not mention the checkout, so the agent picks another name rather than writing the file into the checkout.
19. `accept_design` refuses a frozen test file that is an artifact path with `frozen_test_in_store`.
20. In a project whose configuration names no store, `get_artifact` and `update_artifact` refuse with `store_not_configured`, and Prism keeps every artifact in the checkout as before.
21. When the configured store is unavailable or the checkout's repository name is refused, `get_artifact` and `update_artifact` refuse with the store's own refusal code, such as `store_unavailable`, whose message names the store as configured, and read or write no checkout file.
22. With a store, Prism reads and writes the artifacts it uses itself in the store and never in the checkout: `slice.md` and PlantUML files at design proposal and acceptance, `slice.md` in `update_design_view`, the `recovery.md` that `checkpoint_pause` writes, and the generated `initiative.md`, `review.md`, and roadmap views.
   A recovery note or generated view goes in the scope that holds an artifact other than a generated view in the nearest of its folders where any scope holds one, when only one scope does there, else in the workspace scope, and a view that an earlier generation put in another scope moves there, leaving no copy, the next time it is generated.
   Because a plan folder is named by initiative and slice slugs, `update_initiative` with a store refuses a `create`, `import_map`, or `split` that names a slug beginning with `-` or `_` with `artifact_name_invalid` and changes no record, and for such a slug that a record already holds Prism reads and writes none of its plan files: its design proposal and acceptance are refused with `artifact_name_invalid`, and no generated view is written for it.
   In the same way, a slug whose plan folder collides in letter case, as §14 defines, with the plan folder of another initiative that the store's records hold, with the plan folder of another slice of the same initiative, or with an artifact path that a seen scope holds is refused with `artifact_name_conflict`, `data.path` holding that other initiative's or slice's plan folder, else that artifact path, and a slug whose plan folder's location, in the scope that holds the initiative's plan folder, else the workspace scope, holds more than 120 characters with `/initiative.md`, the longest name Prism writes there, added is refused with `artifact_path_too_long`, `data.location` holding that location with `/initiative.md`; such a slug that a record already holds is treated as above, with that refusal's code.
23. With a store, the review browser lists the artifacts the checkout sees by path in `/api/index`, gives each one's scope label in `artifactScopes`, and serves its store bytes from `/api/artifact`.
   When the store is unavailable or the checkout's repository name is refused, the review browser shows no checkout file under the artifact paths in its listing, search, libraries, glossary, or slice pages, `/api/index` reports the refusal's message in `recordStore.unavailable`, which for an unavailable store names the store as configured, and `/api/artifact` answers an artifact path with `503` and that message instead of the checkout's bytes.

### Sync and concurrent changes

24. Where store sync is on, an `update_artifact` that changed a file schedules the store sync that a record write schedules, so the change is committed and pushed without a further call.
25. A sync merges an artifact that changed on both sides with Git's line merge, and when that conflicts it keeps the upstream artifact, saves the local bytes under the store's sync folder, and names the artifact's path, scope label, and saved copy in the next tool result of each Prism server that uses the store.

### Moving existing artifacts

26. When a Prism tool call whose project root is a checkout first accesses the checkout's store in a server process, before the access proceeds, Prism moves every ordinary tracked file under the checkout's artifact paths, which is each index entry there that `git ls-files -v` tags `H`, a merged (stage 0) entry with neither the skip-worktree nor the assume-unchanged bit and so one whose work-tree changes Git sees, taken with its bytes in the work tree, into its repository's scope, except a frozen test of an accepted design, the record files that the record move takes, and the file at the configured `Roadmap` path, which §28 decides.
   Only such a tool call moves, because only its result carries the report that §29 gives: no other access of the checkout's store, such as a review browser request, the shared review app's reading of every registered project for its project list, a hook, or a tool call whose project root is another checkout, moves, writes, or removes any file for the move or names it in a ledger, and the checkout's next tool call moves and reports its files as though no such access had happened.
   The review browser shows only the artifacts the store holds, as §23 says, and never a checkout file under the artifact paths, so `/api/artifact` answers a path that only the checkout holds with `404`.
   Where the store is available, `/api/index` sorts the files that Git tracks under the checkout's artifact paths and that its work tree holds, other than a skip-worktree entry, a frozen test of an accepted design, and the record files that the record move takes, into kept files and files that a move still decides on: a file is kept when it is an assume-unchanged entry or an unmerged path, which the move passes over with a reason as below, whatever a ledger lists for it, or when a ledger of the repository lists it as kept and none lists it as moved, unless every such ledger kept it as `too_large` or `not_text` and the file in the work tree now holds at most 1 MiB of UTF-8 text, and every other such file is one that a move still decides on, such as a file that no ledger names or one that a ledger lists as moved while the checkout still holds it.
   `recordStore.awaitingMove` gives the number of files that a move still decides on as `files` and a `message` that says those files are still in the checkout and not in the store, that an agent's Prism tool call in the checkout moves them into the store and reports each move or why a file stays, and that an agent session moves the checkout's files once, so a file that Git starts tracking after that move waits for the next session; the browser shows it beside the store's status as a warning, and `/api/index` leaves `awaitingMove` out when that number is 0.
   `recordStore.keptInCheckout` gives the number of kept files as `files` and a `message` that names no file and says those files stay in the checkout until a person settles each, as the report of the move that kept them gave each one's reason, with no tool call to wait for; the browser shows it beside the store's status as a plain note, not a warning, and `/api/index` leaves `keptInCheckout` out when that number is 0.
   The move writes each moved file into the store, with the status record of a moved requirement or ADR, then one ledger file under `artifact-migrations/` naming the repository, each move, and each kept file, and only then removes the moved files from the checkout, so a move interrupted at any point leaves each file in the checkout, the store, or both, names every removed file in a ledger, and leaves no requirement or ADR whose checkout file is gone without its status record; a store location that already holds a moved file's bytes without a status record gets the status that §31 records for a moved file before the checkout file is removed.
   The move removes the moved files from the checkout only once its tool call has answered, right before Prism writes that call's result with the report that §29 gives, and then removes a moved file only while the checkout file still holds the bytes that the move took, its index entry is still one that the move takes, and its store location holds those bytes or bytes that an `update_artifact` of the same tool call wrote there; any other moved file stays in the checkout with the reason `differs`, or `removed_in_store` when its location holds no file, or, when its entry is no longer one that the move takes, as the state of that entry below says.
   A moved file that the work tree no longer holds by then, such as one that an earlier finish of the same move removed before a cancel or a host close stopped it, leaves no checkout copy to compare, so it is reported as moved whenever its store location holds a file, whatever bytes that file holds, such as bytes that the cancelled call's `update_artifact` wrote, and never with the reason `differs`.
   A tool call that Prism refuses, that the host cancels before its result is written, or whose result Prism makes after the host closed its input still writes the store copies, their status records, and the ledger, but removes no checkout file once the cancel or the close is known and carries no report: the checkout's next tool call whose result Prism writes removes the files that remain and reports the whole move, in the same server process as it does after a deferred move, and in a later process through a move that removes each file that a ledger lists as moved, as §27 says.
   Nothing can stop a cancel or a host close from coming between a removal and the result written after it, so a removal that no result named is named later: the move of each later server process reports as moved earlier, from checkout path to the store location that a ledger of the repository lists for it, each path under the checkout's artifact paths that `git ls-files --deleted` lists from the checkout's index and whose entry is one that the move takes, which is each ordinary entry whose path the work tree lacks, that such a ledger lists as moved, and whose store location holds a file, whatever bytes that file holds, and writes, removes, and names in a new ledger nothing for such a path.
   A path moved earlier is reported once in each server process, in the result that carries that process's move report as §29 says, and again in every later process for as long as `git ls-files --deleted` lists it as an entry that the move takes, which stops only when a person stages or commits its deletion, which `git add -A` and `git commit -a` do for such an entry, or its entry stops being one that the move takes, such as when Git makes it a skip-worktree entry, so the report never names a path whose removal Git's ordinary staging cannot take.
   A skip-worktree entry is an index entry that Git keeps out of the work tree on purpose, one whose skip-worktree bit is set, which `git ls-files -t` tags `S`, such as each file that a sparse checkout leaves out or one that `git update-index --skip-worktree` marks: Git takes no change of the work tree at its path, so a removal there would neither show in `git status` nor be staged, and its bytes stay in the checkout's index and branch.
   A skip-worktree entry never moves, is never removed, is never reported as moved, moved earlier, or kept, is named in no ledger, and is counted in neither `recordStore.awaitingMove` nor `recordStore.keptInCheckout`, whatever the work tree holds at its path and whatever a ledger lists for that path, so no move report or browser notice names it for its own sake; once Git puts the file back into the work tree and clears the bit, such as after `git sparse-checkout disable`, a later session's move decides it as any other tracked file, by §27 and §28 when a ledger lists its path as moved.
   Every other index entry is one that the move does not take: `git ls-files -v` tags a skip-worktree entry `S`, or `s` when its assume-unchanged bit is also set, an entry with only the assume-unchanged bit `h`, and each stage of an unmerged path `M`, and the move never moves, removes, or names in a ledger such an entry and never reports it as moved or moved earlier, whatever the work tree holds at its path and whatever a ledger lists for that path.
   An assume-unchanged entry, one whose assume-unchanged bit is set, such as by `git update-index --assume-unchanged`, is one whose work-tree changes Git does not look for: `git status`, `git add -A`, and `git commit -a` neither show nor stage an edit or a removal at its path, although `git ls-files --deleted` lists it while the work tree lacks its file, so a removal there could not be committed the ordinary way and would be reported as moved earlier in every session.
   The report names an assume-unchanged entry, when its work tree holds a file at its path or a ledger of the repository lists that path as moved, by its checkout path with the reason `assume_unchanged` and the remedy that `git update-index --no-assume-unchanged <path>` clears the bit, after which a later session's move decides it as any other tracked file, or reports it as moved earlier when the work tree lacks it.
   An unmerged path is one that the index holds in stages 1 to 3 instead of one merged entry, because a merge, rebase, `git am`, cherry-pick, revert, or `git stash pop` stopped on its conflict, and its work-tree file may hold conflict markers or be gone: the report names it once, when its work tree holds a file at its path or a ledger of the repository lists that path as moved, by its checkout path with the reason `unmerged` and the remedy that a person resolves the conflict and stages the result with `git add`, or ends the operation, after which a later session's move decides it.
   A file under the artifact paths that Git does not track never moves, is never removed, and is named in no ledger, whatever §28 would decide for it: the report lists each untracked file that Git does not ignore, such as a draft, by its checkout path with the reason `untracked` and the remedy, that a person commits it for a later first access to move or writes it with `update_artifact`, and gives only the number of ignored files, without naming them; when Git cannot list the checkout's files, the move takes no file and the report says so.
   A tracked file other than the roadmap view that holds more than 1 MiB, the limit that §16 sets for content, stays in the checkout with the reason `too_large`, and one that is not UTF-8 text, as §11 decides, with the reason `not_text`, whatever its kind, a plan folder's probe output or image included, so the store takes only what `get_artifact` reads back and `update_artifact` could write; the ledger lists either as kept, and the report names its checkout path and, for `too_large`, its size in bytes.
   With a store, a configured `Requirements`, `ADRs`, or `Plans` folder that is the project root, such as `.` or `docs/..`, or that is or holds the folder of a component declared under `## Components` would take the source tree, so every record operation and both artifact tools refuse the checkout with `artifact_folder_invalid` before Prism moves, removes, or writes any file, with `data.key` holding the configured key, `data.folder` the folder as resolved, `.` for the project root, `data.component` the component whose folder it is or holds when there is one, and a message that asks for a folder below the project root that holds no component's folder, or `n/a`; a value that leaves the project root already names no folder.
   Where store sync is on and the store's branch has an upstream, the move decides every file against the store as pulled from its remote: before it decides any file it completes a sync that fetches and merges the upstream, so `moved`, `differs`, `removed_in_store`, and the ledger check of §27 read what other machines pushed, and the sync that its writes schedule, as §24 says, pushes the moves, while a change that another machine pushes in the meantime meets them in the store's merge as §25 says, which loses neither side.
   When that sync cannot complete the pull, such as when the remote cannot be reached (`fetch_failed`) or its merge stops (`merge_failed`), the move is deferred: the access proceeds, the move moves, removes, and records nothing, the tool result says that the checkout's artifacts wait for a pull from the store's remote and gives the sync's state but no Git output, and each later tool call of the checkout in the process tries the move again with a pull of its own until one completes; a pull that completes only after its tool call returned lets the move write the store copies, their status records, and its ledger but remove no checkout file, and the checkout's next tool call removes the files as §27 says and reports them.
   While Git has a merge, rebase, `git am`, cherry-pick, or revert in progress in the checkout, as `git status` reports it from a `MERGE_HEAD`, `rebase-merge`, `rebase-apply`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, or `sequencer/todo` file that `git rev-parse --git-path` locates for the checkout, the whole move waits, because the work tree then holds bytes that no commit holds yet and the operation's next commit takes every staged change, so a removal could not be committed on its own: the access proceeds, the move moves, removes, records, and reports as moved earlier nothing, the tool result names the operation as `merge`, `rebase`, `am`, `cherry-pick`, or `revert`, says that it is in progress in the checkout and that the checkout's artifacts wait until it is finished or aborted, and each later tool call of the checkout in the process looks again, before any pull of the store, until one finds no operation in progress and moves.
   A move's finishing step removes no checkout file while such an operation is in progress, such as one that started after the move decided its files, and its result says that the move waits as above; the checkout's first later tool call whose finishing step finds none removes the files that remain and reports the whole move.
27. A path that a ledger file already lists as moved for the repository is never written into the store again: a checkout file at that path whose store location holds the same bytes, as a move interrupted between its ledger and its removals leaves it, is removed as §28 says, and one whose location holds other bytes or no file stays with the reason `differs` or `removed_in_store`.
28. A checkout file whose store location already holds the same bytes is removed, reported as moved, and listed in the ledger as a move; one whose location holds other bytes, whose path the workspace scope holds, or whose ledger-listed artifact the store no longer holds stays in the checkout, and the report names both locations and the reason `differs`, `workspace_holds`, or `removed_in_store`.
   A checkout file inside a configured `Requirements`, `ADRs`, or `Plans` folder, or at the configured `Glossary` or `Roadmap` path, whose path has no well-formed name is never moved or removed: it stays in the checkout, the ledger lists it as kept, and the report names its checkout path and the reason `name_invalid`.
   A checkout file that the move would create at a path that collides in letter case, as §14 defines, with an artifact path that a seen scope holds, or with the path of another checkout file that the move would create, is never moved or removed, so both files of such a pair in the checkout stay: it stays in the checkout, the ledger lists it as kept, and the report names its checkout path, the other path, and the reason `name_conflict`.
   A checkout file whose location in its repository's scope would hold more than 120 characters stays in the same way, and the report names its checkout path, that location, and the reason `path_too_long`.
   A well-formed file at the configured `Roadmap` path is a view of the roadmap record, which the record move takes into the store, so it never moves into a repository's scope and only this rule decides it: when the store holds a roadmap record that `get_roadmap` reports valid, Prism first writes the view generated from that record at `artifacts/roadmap.md` as `update_roadmap` writes it, replacing a missing or generated view and never a hand-written one, and a checkout file with the same bytes as the view the store then holds is removed, reported as moved to that location, and listed in the ledger as a move.
   A file at the configured `Roadmap` path with other bytes, such as a hand-edited or stale view, stays in the checkout with the reason `view_differs`, and one whose store holds no valid roadmap record stays with the reason `no_roadmap_record`; the ledger lists either as kept, and the report names its checkout path, the store's view location for `view_differs`, and the remedy, that content the roadmap record lacks goes into the record through `update_roadmap` before a person removes the file, so nothing a person wrote is lost silently.

The first result that Prism writes for a tool call of the checkout after a move, the result right before which §26 removes the move's files, reports the moved files from checkout path to store location, apart from them the files that §26 reports as moved earlier, in the same form, the kept and untracked files, the assume-unchanged entries and unmerged paths that §26 names, and each tracked file left in the checkout, by `git ls-files`, whose text names the former path of a moved file or a file moved earlier, or the configured folder of a kind that lost either, as `<file>:<line>` with at most 20 of its line numbers, separated by commas, followed by ` and <n> more lines` when more of its lines do, listing at most 200 such files and the count of the rest.
   The report's text holds at most 32 KiB of UTF-8: when its entries would take more, it leaves out entries from the end, and its last line gives the number of entries it left out and names the move's ledger file below `artifact-migrations/` in the store, which lists every move and kept file, when the move wrote one.

### Status at gates

30. A requirement's or ADR's written status is the text after `Status:` on the first line beginning with `Status:` before its first `## ` heading.
31. Prism records each requirement's and ADR's status in the store: `Draft` for a new requirement, `Proposed` for a new ADR, the written status for a moved file, and afterwards only what a gate answer sets.
32. `get_artifact` and the `artifacts` entries return a requirement's or ADR's recorded status as `status`, and when the written status differs, `get_artifact` and the artifact's entry in the `update_artifact` result that wrote it return `statusMismatch` with `written`, `recorded`, and a message that names the gate that changes it; neither refuses, and the review browser shows the recorded status.
33. `update_artifact` operation `ask_approval` (`path`, optional `status`, default `Approved`, `question`, `context`) records a pending approval gate on a requirement or ADR at its current version and returns its id as `gate` in the artifact's entry of the result; it is refused with `status_by_ship` for `Accepted` on an ADR, with `nothing_to_approve` when the status equals the recorded one and the bytes equal the accepted version, and with `not_a_status_artifact` for any other file.
34. The review browser's Attention lists each pending approval gate of the artifacts the checkout sees under `needsYou` as an item of `type` `gate` and `kind` `approval` with its `id`, `question`, `context`, and `artifact` holding its `path` and `scope`, and the person answers it through the review app's actions as every other gate: `GET /api/actions?target=approval:<id>` lists one action, `gate.answer`, whose `target` is `approval:<id>`, whose fields are a required `choice` of `approve` or `request-changes` and a `note` of at most 4000 characters that `request-changes` requires, and whose `revision` is the artifact's current version.
   `POST /api/actions/apply` with `{ action: "gate.answer", target: "approval:<id>", input: { choice, note }, revision }` applies it with the checks of every other action: a request that is not JSON from the review page's own origin is refused with `403` `origin_refused`, one without the page's write session with `403` `write_forbidden`, an id that names no pending approval gate of an artifact the checkout sees, an answered one included, with `404` `unknown_target`, a `revision` other than the artifact's current version with `409` `stale_revision`, and an input the action does not accept with `400` `invalid_input`, and a refused request changes nothing.
   An applied answer returns the registry's history entry as `applied`, with `id`, `action` `gate.answer`, `target`, `before` null, `after` holding `choice` and `note`, `at`, `by`, and `via` `review-app`, records that entry in the artifact's status record and in no initiative's history, and `get_artifact` returns its id as `entry` in `latestAnswer`.
   `/api/gates/answer` does not exist: every request to it, whatever its body, answers `404` and changes nothing.
35. Approving rewrites the artifact's `Status:` line to the gate's status and, for `Approved`, its `Approved:` line to the answer's date, adding one after the `Status:` line when it has none, then records the status, the accepted version, and `approval` with the gate, the time, and who approved as `by` with the checkout's Git `user.name` as `name` and the machine's host name as `host`, which `get_artifact` returns.
36. While the artifact's version differs from the version its gate was asked at, the `gate.answer` listing shows the action unavailable with a reason that says the artifact changed, and applying it is refused with `409` and code `artifact_changed`; applying it in a checkout whose Git has no `user.name` is refused with `409` and code `author_unknown`, and neither refusal changes anything.
37. `wait_for_user_gate` takes `artifact` (and optional `scope`) in place of `initiative` and waits for that artifact's approval gates as it waits for an initiative's.
   An approval answer reaches the checkout that asked its gate, the project root whose `ask_approval` recorded it, which Prism remembers on that machine and never in the store: the prompt hook of both hosts adds the answer, `approve` or `request-changes` with its note, to the next message of any session in that checkout until the checkout has received it once, through such a message, a session start, a `wait_for_user_gate` result, or a `get_artifact` read of the file that returned it as `latestAnswer`, however long ago the person answered.
   No other checkout, on that machine or another, is handed the answer, and every checkout that sees the artifact reads its latest answer as `get_artifact`'s `latestAnswer` with `gate`, `status`, `choice`, `note`, `answeredAt`, `by`, and `entry`.
   A session that starts or resumes in a checkout is told each approval gate that checkout asked and the person has not answered, with its id and the artifact's path, so that it waits on it again.
38. The accepted version of an artifact is its bytes at its latest approval, at the `accept_proposal` that accepted designs of the slices whose folders hold it, or at the ship that accepted it; `get_artifact` returns `acceptedVersion` and `changedSinceAccepted`, and with `accepted` true reads the accepted bytes.

### Review in the browser

39. `/api/artifact` for a store artifact also returns `artifact` with `scope`, `version`, `accepted` (`version` and `content`, or null), `changed`, and `comments`, and the browser shows the changed lines against the accepted version, or the whole file as added when it has none.
40. `POST /api/artifact/comments` with JSON `{ path, scope, version, line, text }` from the review page stores one new file per comment under `artifact-comments/<location>/` holding `location`, `version`, `line`, `text`, `author` with the checkout's Git `user.name` as `name` and the host name as `host`, and `at`, and returns it with `path` and `scope` added and status `201`.
41. A comment is refused with `403` when it is not JSON from the review page's own origin, `404` for an artifact the checkout does not see, `400` for text that is empty or above 4000 characters, and `409` `author_unknown` when Git has no `user.name`.
42. Every reader of an artifact, in the browser through `/api/artifact` and in `get_artifact`, gets its comments, oldest first, including comments that a sync brought from other machines.

### Accepting ADRs at ship

43. With a store, `ship` takes `afterGate`, a `correctness` gate of the initiative that the review browser answered `approve`, and is refused with `ship_unconfirmed` without one.
44. On ship, each ADR whose recorded status is `Proposed` and that a Markdown link in any `slice.md` of the initiative names becomes `Accepted`: Prism rewrites its `Status:` line, records the status with the gate, and records `acceptance` with the gate and `verifiedBy`, the `slice`, `repository`, and `commit` of each leaf slice's latest passing verification run, which `get_artifact` returns; the ship result lists the accepted ADRs under `acceptedAdrs` with `path`, `scope`, and `verifiedBy`, and a cited ADR with another recorded status stays as it is.

### Guidance

45. The workflow skills tell agents in a project with a store to read and write descriptive artifacts only through `get_artifact` and `update_artifact`, to leave status lines to gates, to ask requirement approval through `ask_approval`, and to ship after a `correctness` gate, while a project without a store keeps editing them in the checkout.
46. The workflow skill defines **Portable name** once in its Common terms, without naming any store location, as a file, folder, or identifier name that agents choose in every project, with or without a store, so that a repository shared by Windows, macOS, and Linux engineers checks out everywhere: an ASCII letter or digit first, then only ASCII letters, digits, `.`, `_`, and `-`, no `.` or `.lock` ending, no Windows device name such as `con`, `aux`, `nul`, `com1`, or `lpt1` before the first `.` in any letter case, no other name in the same folder that differs from it only in letter case, a project-relative path of at most 100 characters, and, for an initiative or slice identifier, no `.` and at most 40 characters.
   Every workflow skill that chooses a new file, folder, or identifier name, which are `design` for slice slugs, slice folders, tests, probes, and diagrams, `ideate` and `triage` for initiative identifiers, `setup` for configured paths, `implement` and `refactor` for files that no design named, and `write-adr`, `write-requirements`, `write-feature`, `write-contracts`, `write-step-definitions`, and `write-user-docs` for the files they create, tells agents to choose portable names by linking that term rather than restating the rule, while `orchestrate` takes the identifiers that ideation and design chose and names none of its own.
