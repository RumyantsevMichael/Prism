# Workspace artifacts in the store

## Outcome

A workspace's descriptive artifacts live in its shared store, scoped to the workspace, a repository, or a component, reviewed in Prism with diffs and comments, and changed in status only at gates, while executable artifacts stay with the code.

## Design questions settled

- Agents read and write store artifacts only through Prism tools, addressed by the project-relative path the checkout's configured paths give them, because writes outside the working folder ask for approval or fail in sandboxed hosts, and only a tool write lets Prism lock, sync, and check status ([store-artifacts ADR](../../ADRs/workflow-records/store-artifacts.md)).
- Configured paths map to fixed kind folders in the store, and a repository's or component's artifacts live in that scope's own folder, so two repositories never share a location, while within what one checkout sees each path names one artifact.
- Concurrent changes to one Markdown artifact merge by Git's line merge, which combines changes to different sentences of a one-sentence-per-line file (probe below), and a line that changed differently on both sides falls back to the whole-file rule that records use.
- Artifact names follow one positive name form instead of a list of dangerous names, so every `.git` variant, Git's short name `git~1`, dotfiles such as `.gitignore`, temporary files, and invisible characters are refused by one rule, at the cost of refusing names with spaces or non-Latin letters.
- The name form also refuses the two kinds of name that Git for Windows refuses to check out while Git elsewhere adds them, a Windows device name before the first `.` and a `.` at the end, because one such name written from Linux or macOS would stop the store on every Windows machine of the workspace (probe below).
- Two paths that differ only in letter case are one file on the default macOS and Windows file systems, so no update creates a path that collides in letter case with one the checkout sees, while a colliding pair that the store already holds stays as it is, so that no bytes are lost before a person removes one.
- Store paths stay short enough for a store's managed clone on Windows to check out without Git's `core.longpaths`, so an artifact's location holds at most 120 characters, refused with a code of its own, `artifact_path_too_long`, rather than `artifact_name_invalid`, because no single name breaks a rule and the remedy is a shorter path or another scope (probe below).
- Agents choose portable names in every project, not only in one with a store, because one repository is often checked out on Windows, macOS, and Linux, and the skills state the rule once as a Common term without saying how Prism stores anything; the guidance asks for a project-relative path of at most 100 characters and identifiers of at most 40, which under the default configured paths keeps a repository-scope location within §16's 120 characters for a repository name of at most 11 characters, while the tools enforce the exact limits.
- Prism names plan folders from initiative and slice slugs, so a slug is checked against the name rules when it is created, before any plan file exists, rather than when Prism first writes into its folder.
- Prism's lock and temporary files stay beside the store files they guard, because the ignore file that Prism writes into a store lists `*.lock` and `.*.tmp`, so the store's Git would leave out an artifact with such a name wherever the locks lived; the name form already refuses `.*.tmp`, which begins with `.`, and only the `.lock` ending is reserved besides, in any letter case because a case-insensitive file system makes `x.LOCK` the lock file of `x` (probe below).
- Code repositories keep their configured paths, which stay the artifacts' addresses, and the move reports each tracked file that still names a moved path, so a person updates the instructions instead of Prism rewriting them.
- A move removes checkout files only right before Prism writes a tool result that reports them, rather than carrying its report in a refusal, because a cancelled call or one answered after the host closed its input has no result that reaches the agent, and one rule then covers refused, cancelled, and closed calls without a removal that no result names.
- Nothing in Prism can stop a cancel or a host close from coming between a move's removal of a checkout file and the result that reports it, so the first tool call of each later session reports as moved earlier every such file whose deletion Git's index still lists and whose store location holds a file, and stops only once a person stages or commits the deletion, because that is the one sign that a person has seen the removal, while the order of the reference scan and the removals, which only narrows that window, is left to the implementation.
- The review browser counts apart the files that a move keeps for good, such as an image in a plan folder, and shows them as a plain note without names, because a warning that a tool call will move them would never clear, while a file that a person has since made text again counts as waiting once more.
- Status changes at gates are recorded beside the artifact in the store ([artifact status ADR](../../ADRs/workflow-records/artifact-status-at-gates.md)).
- An approval answer is the review app's `gate.answer` action on a target `approval:<gate id>`, and a comment is its `artifact.comment` action on a target `artifact:<scope label>:<path>`, which no artifact name or scope label can make ambiguous because neither holds a `:`, applied through the same route, origin check, and write session as every other gate answer, and neither keeps a route of its own, because review-app-actions.md§9 accepts a change from the review app only as an action ([review-app-actions ADR](../../ADRs/workflow-records/review-app-actions.md)).
  Both actions take the artifact's version as their revision, so a page that read an older artifact is refused as stale, and each entry is recorded with the artifact, an approval in its status record and a comment in its own file, because neither belongs to an initiative; the person accepted the approval's recording, which [review-app-actions.md§15](../../requirements/review-app-actions.md#15) states with the partial supersession in the [artifact-status-at-gates ADR](../../ADRs/workflow-records/artifact-status-at-gates.md), while the comment's recording waits on the person's answer to the proposed amendment of review-app-actions.md§15 in [review-app-actions-amendment.md](review-app-actions-amendment.md).
- An approval target keeps naming only the gate id, and an id that more than one pending gate holds is refused rather than resolved by scope and path, because two pending gates share an id only when a status record was copied, by a damaged sync or a `move_scope` stopped between its writes and its removals, and then either copy may be the one nobody asked about, so the agent removes the copy and asks again before the person answers.
- An approval and a comment show in Attention's recent changes as every other applied action does, read from the record that keeps each, because review-app-actions.md§8 requires every applied action in the attention feed whatever history keeps it, and their actions routes answer an unavailable store with `503`, as an artifact read does, rather than with a refusal that blames the request.
- A comment belongs to its artifact rather than to its location, as the artifact's status record does: it moves with the artifact to another scope and is removed with it, because a removed artifact has no page that could show its comments, and a second place that shows the comments of removed files is a surface that no requirement asks for.
  So that no comment goes silently, the result of a removal counts the comments it removed for the agent, which reads them with the file through `get_artifact` before it removes the file, and where store sync is on the store's own history keeps the removed comment files.
- A change that one machine makes to an artifact while another machine moves or removes it, to its bytes, its status record, or its comments, such as an approval or a comment, belongs to the artifact by an identity that the store keeps beside each artifact, which creating the artifact writes, a move takes along, and removing it deletes, because neither a path nor bytes tell a sync which file a change was made on: a move looks like a removal beside an unrelated file at the same path in another scope, which another repository may hold, and a removal followed by a write at the same path looks like an edit, whose line merge would put an approval and a comment made on the removed file onto a file that nobody reviewed.
  A sync therefore merges by identity rather than by path, finds a moved artifact where the other side's store holds its identity, and needs no forward at the old location, so no removal can leave a forward that leads to a later file.
- A removal conflicts only with an edit of the removed file's bytes, because a comment, an approval asked, or a status change says nothing new about the file's text, while a person's deliberate removal does: the removal then stands and the other change is saved and named, and where it meets an upstream edit, the upstream wins as in every conflict and the undone removal is named, as is every other local removal, move, or edit that a sync does not keep, since the person can redo only what they hear was undone.
  An artifact stored before identities has the one that its location gives, so no store needs a migration, a store written before this rule merges as it did, and a later file at the same path still gets a new identity of its own.
  The followed change merges as it would have merged at the new location, so a status record that only one side changed takes that change, and one that both sides changed keeps the upstream record and saves and names the local one, as a status record that two machines changed at one location does, and neither record is lost.
  A status record or comment whose artifact a sync finds removed leaves the store, saved aside and named in the next result as a line conflict is, because no page could show it and the store would otherwise keep a record that no reader shows.
  A location that the merge would give to two artifacts, as where one machine removed a file and wrote another at its path while the other machine changed the first, keeps the upstream's artifact whole, as a line conflict keeps the upstream's bytes, and saves and names the other's changes, so neither file takes the other's bytes, status, or comments.
  So a merged store holds no status record or comment without its artifact, and the next update that creates an artifact at a location removes and counts only what reached it otherwise, such as a file put there by hand, so a file written later at a path never inherits an earlier file's comments.
- The Review card lists every line of the current version with its number, because the changes number only the lines near a change, a file that matches its accepted version, the most common state after an approval, shows none, and the rendered document numbers nothing.
- A comment's `line` takes white space around its digits, because the review app's actions trim every text field and a pasted ` 12` names line 12 without doubt, while any other character, a sign or a non-ASCII digit included, is refused.
- A reader takes a comment file or a status record's history entry only in the exact form that Prism writes, with the history entry's author equal to the author the comment or answer names and a time in the one form whose text order is its time order, because a store sync brings files that no Prism checked and Recent changes sorts and shows them beside every initiative's history; an entry dated more than five minutes ahead of the reading clock waits, which allows for machines whose clocks differ a little and stops a file from pinning itself to the top of the list.
  The note that names a comment a sync saved aside quotes it only in that same form, and names any other saved file by its path alone, because the note goes into the agent's context in Prism's voice, where text that anyone who writes to the shared store planted would read as a person's comment.
- Comment files are opened without following a link and checked for size from the open file, as Prism's other store readers do, because every open page reads them every 1.5 seconds and a store sync can bring a file of any size.
- Anyone who can push to a store can push files of any size and in any number, so one rule bounds them all rather than each reader guarding itself: every kind of store file has one size bound well above what Prism writes, an artifact has a bound on its comments, and every reader and every sync applies the same bounds.
  A sync refuses an upstream over a bound as it refuses an entry that no store may hold, because the file then never reaches a disk that a reader reads, and a writer who can push could already stop a sync with a link, while a local file over a bound stays out of every commit, as a path too long for some machine does.
  Comments are the one bound that two honest machines can reach together, each staying below it, so a merge past it saves and names this machine's surplus instead of refusing the upstream.
  `JSON.parse` of 16 MiB of empty objects grows the heap by about 360 MiB, so no JSON kind is bounded above 16 MiB, and the depth check takes memory only by depth, so a file within its bound never takes more than `JSON.parse` does (probe below).

## Contract

### Artifact paths and store layout

1. In a checkout whose `.prism/workflow.md` names a store under `## Workspace`, a project-relative path, with its `.` and `..` components resolved, is an artifact path when it equals the configured `Glossary` or `Roadmap` path or lies inside the configured `Requirements`, `ADRs`, or `Plans` folder, lies inside neither the configured `Feature files` nor `User guide` folder, and has a well-formed name; a path names its kind by the longest configured path that contains it, and a key set to `n/a` names no kind.
   A path has a well-formed name when every component of it below its configured folder, and the file name of the configured `Glossary` or `Roadmap` path, begins with an ASCII letter or digit, holds only ASCII letters, digits, `.`, `_`, and `-`, does not end in `.`, does not end in `.lock` in any letter case, the name of the lock that store sync takes beside a store file, and is no Windows device name, which is a component whose part before its first `.`, or the whole component when it has none, is `con`, `prn`, `aux`, `nul`, `com0` to `com9`, or `lpt0` to `lpt9` in any letter case, such as `aux`, `NUL.txt`, or `Lpt9.tar.gz`; no listing shows a file whose path has no well-formed name.
2. A store holds artifacts under `artifacts/` in scope folders: the workspace scope at `artifacts/`, a repository at `artifacts/repositories/<repository>/`, and a component at `artifacts/repositories/<repository>/components/<component>/`.
   Because repository and component names name store folders, and a repository's name also names its registration file `repositories/<repository>.json`, each is a portable name: Prism already takes only 1 to 64 lowercase ASCII letters, digits, `-`, and `_` that begin and end with a letter or digit, which meets the §1 name form and keeps the registration file within 82 characters and the deepest scope folder within 163 characters below the store's folder, inside the bounds of §3, while §16 bounds each artifact location in a scope, and a name must also be no Windows device name in the §1 sense, `con`, `prn`, `aux`, `nul`, `com0` to `com9`, or `lpt0` to `lpt9`.
   A checkout whose `Repository` name is a Windows device name is refused as an invalid name is, with `repository_name_invalid`, by every record operation and by both artifact tools before Prism registers the name or writes any file, whether or not the store already registers it; `data.proposed` holds a portable name that the store would accept, and a registration that the store already holds under such a name accepts no checkout and keeps no remote from registering under another name.
   A `write` that creates an artifact in a component scope whose component name is a Windows device name, whether its `scope` input or its nearest ancestor folder as §14 decides names that scope, and a `move_scope` into such a scope are refused with `component_name_invalid`, `data.component` holding the name, and a message that asks to rename the component under `## Components` in `.prism/workflow.md` or to choose another scope; a component folder of such a name that the store already holds stays seen, and each of its artifacts is listed, read, written with its version, edited, removed, and moved to another scope by its path.
3. Inside a scope folder an artifact lives at `requirements/<rest>`, `adrs/<rest>`, `plans/<rest>`, or `glossary.md`, where `<rest>` is the artifact path below its configured folder, and the roadmap view lives only at `artifacts/roadmap.md`; the artifact's location is its path below `artifacts/`.
   An artifact's location holds at most 120 characters, and every store path that Prism derives from a location, such as a comment file or a status record, holds at most 186 characters below the store's folder, with each of its folders at most 174.
4. A scope is reported as `{ kind, label }` with `kind` `workspace`, `repository`, or `component`, `repository` and `component` names where they apply, and `label` `workspace`, `<repository>`, or `<repository>/<component>`.
5. A checkout sees the workspace scope, its repository's scope under its accepted `Repository` name, and the scope of every component folder of its repository that the store holds.
6. A path resolves to the one scope the checkout sees that holds it; when more than one does, a read or update without `scope` is refused with `artifact_ambiguous` and `data.scopes` listing their labels, and a `scope` input picks one.
7. A `scope` input is `"workspace"`, `"repository"`, or `"component"` with a `component` name; a component that the checkout's `## Components` does not declare is refused with `component_unknown`, and any other value with `scope_invalid`.

### Reading artifacts

8. `get_artifact` with `path` naming a file returns `path`, `scope`, `kind`, `version` (`sha256:` and the hex SHA-256 of the file's bytes), `bytes`, `totalLines`, `offset`, `content`, and `nextOffset`, which is null on the last page.
9. A read returns the text of whole lines from `offset` (1-based, default 1), with their line endings, up to `limit` lines (default 2000) and at most 64 KiB, and always at least one line, so the pages of a long file joined in order give its text.
   That text is the stored bytes decoded as UTF-8 exactly, a leading byte order mark and every carriage return included, so a `write` of the joined pages stores the same bytes and version, and an `edit` changes only the text it replaces.
10. `get_artifact` without `path`, or with `path` naming a folder, lists every artifact the checkout sees below it as `artifacts` entries of `path`, `scope`, `kind`, `version`, and `bytes`, sorted by path and then scope label, at most 2000 entries with `truncated` true when more exist.
11. A path no seen scope holds is refused with `artifact_not_found`, and a file that is not UTF-8 text with `artifact_not_text`.
   Every artifact is a regular file: a location that holds a symbolic link or a special file such as a pipe or device, or lies below a symbolic link, is never opened or followed, listings leave it out, and every read and operation that names it is refused at once with `invalid_path`.

### Writing artifacts

12. `update_artifact` takes `operations`, at most 50, each one of `write` (`path`, `content`, `expectedVersion`, optional `scope`), `edit` (`path`, `expectedVersion`, `edits` of `oldText` and `newText`), `remove` (`path`, `expectedVersion`), and `move_scope` (`path`, `expectedVersion`, `scope`, optional `component`), and returns `artifacts` with each touched artifact's `path`, `scope`, and new `version`, or `removed` true.
13. `expectedVersion` is the version last read, or null to create; any other mismatch with the store is refused with `version_conflict` and `data.version` holding the current version or null.
   Store sync replaces no artifact file between an update's first version check and its last write, so an upstream change either lands before the update, which is then checked against it, or reaches the store's merge as a change made concurrently with the update, and never vanishes under the update's write.
   An update's changes reach the store's history together: no store commit, local or pushed, holds some of one update's changes without the rest, so another machine sees an update, such as both locations of a `move_scope`, whole or not at all.
14. A created artifact takes the given scope, else the scope of its nearest ancestor folder that one seen scope holds, else the workspace scope, and creating a path that another seen scope already holds is refused with `artifact_exists` and `data.scope`.
   Two artifact paths of one kind collide in letter case when some folder or file of one, taken with the folders above it, equals the same part of the other only when ASCII letter case is ignored, such as `docs/plans/x/Plan.md` and `docs/plans/x/plan.md`, or `docs/plans/X/a.md` and `docs/plans/x/b.md`; a `write` that creates an artifact, and a `move_scope`, whose path collides in letter case with an artifact path that a seen scope holds before the update, or with the path of another `write` of the same update, is refused with `artifact_name_conflict` and `data.path` holding that other path, so a rename that changes only letter case takes two updates, a `remove` and then a `write`.
   A colliding pair that the store already holds, such as one that two machines created before either synced, stays as it is: a listing shows each path, and each is read, written with its version, edited, and removed by its own path.
15. Each `edit` replaces one occurrence of `oldText` that occurs exactly once in the text as earlier edits left it, and is refused with `edit_not_applied` and `data.edit` holding its index otherwise.
16. Content is UTF-8 text of at most 1 MiB, refused with `artifact_too_large` above it.
   A `write` that creates an artifact, and a `move_scope`, whose location in the scope the artifact would take holds more than 120 characters is refused with `artifact_path_too_long`, `data.location` holding that location, `data.limit` 120, and a message that asks for a shorter path or a scope with a shorter folder; a longer artifact that the store already holds stays listed, read, written with its version, edited, and removed by its path.
17. Prism checks every operation of an update before it changes any file, and a refused update changes no file.
   A `write` whose location is a folder that holds artifacts, lies below a file that the store holds, or lies below the location of another `write` of the same update is refused with `invalid_path`, so every location an update writes ends as a regular file.

### Where artifacts are kept

18. Feature files, step definitions, frozen tests, executable contracts, and user documentation are not artifact paths: `get_artifact` and `update_artifact` refuse them, and every other path outside the artifact paths, with `not_an_artifact`, whose message says the file stays in the checkout.
   A path that would be an artifact path but for its name is refused by every read and operation of both tools with `artifact_name_invalid`, whose `data.invalidName` holds the first component that breaks the name form and whose message states the form, an ASCII letter or digit first, then only ASCII letters, digits, `.`, `_`, and `-`, no `.` or `.lock` ending, and no Windows device name, and does not mention the checkout, so the agent picks another name rather than writing the file into the checkout.
19. `accept_design` refuses a frozen test file that is an artifact path with `frozen_test_in_store`.
20. In a project whose configuration names no store, `get_artifact` and `update_artifact` refuse with `store_not_configured`, and Prism keeps every artifact in the checkout as before.
21. When the configured store is unavailable or the checkout's repository name is refused, `get_artifact` and `update_artifact` refuse with the store's own refusal code, such as `store_unavailable`, whose message names the store as configured, and read or write no checkout file.
22. With a store, Prism reads and writes the artifacts it uses itself in the store and never in the checkout: `slice.md` and PlantUML files at design proposal and acceptance, `slice.md` in `update_design_view`, the `recovery.md` that `checkpoint_pause` writes, and the generated `initiative.md`, `review.md`, and roadmap views.
   A recovery note or generated view goes in the scope that holds an artifact other than a generated view in the nearest of its folders where any scope holds one, when only one scope does there, else in the workspace scope, and a view that an earlier generation put in another scope moves there, leaving no copy, the next time it is generated.
   Because a plan folder is named by initiative and slice slugs, `update_initiative` with a store refuses a `create`, `import_map`, or `split` that names a slug beginning with `-` or `_` with `artifact_name_invalid` and changes no record, and for such a slug that a record already holds Prism reads and writes none of its plan files: its design proposal and acceptance are refused with `artifact_name_invalid`, and no generated view is written for it.
   In the same way, a slug whose plan folder collides in letter case, as §14 defines, with the plan folder of another initiative that the store's records hold, with the plan folder of another slice of the same initiative, or with an artifact path that a seen scope holds is refused with `artifact_name_conflict`, `data.path` holding that other initiative's or slice's plan folder, else that artifact path, and a slug whose plan folder's location, in the scope that holds the initiative's plan folder, else the workspace scope, holds more than 120 characters with `/initiative.md`, the longest name Prism writes there, added is refused with `artifact_path_too_long`, `data.location` holding that location with `/initiative.md`; such a slug that a record already holds is treated as above, with that refusal's code.
23. With a store, the review browser lists the artifacts the checkout sees by path in `/api/index`, gives each one's scope label in `artifactScopes`, and serves its store bytes from `/api/artifact`.
   When the store is unavailable or the checkout's repository name is refused, the review browser shows no checkout file under the artifact paths in its listing, search, libraries, glossary, or slice pages, `/api/index` reports the refusal's message in `recordStore.unavailable`, which for an unavailable store names the store as configured, and `/api/artifact` answers an artifact path with `503` and that message instead of the checkout's bytes.

### Sync and concurrent changes

24. Where store sync is on, an `update_artifact` that changed a file schedules the store sync that a record write schedules, so the change is committed and pushed without a further call.
25. A sync merges an artifact that changed on both sides with Git's line merge, and when that conflicts it keeps the upstream artifact, saves the local bytes under the store's sync folder, and names the artifact's path, scope label, and saved copy in the next tool result of each Prism server that uses the store.
   Every artifact in the store has an identity, which the store keeps beside it in the file `artifact-identity/<location>` as one line of JSON, an object whose only key `id` holds 32 lowercase hexadecimal digits, and which a sync shares as it shares a status record: every write that creates an artifact at a location that holds none, by `update_artifact`, by the move of a checkout's files that §26 states, or as Prism writes a file of its own, writes a new random identity there in the same update, replacing whatever entry stands there; a move to another scope, by `move_scope` or as §22 moves a generated view, takes the identity to the new location in the same update and leaves no file of the artifact at the old one; a removal, by `remove` or as Prism removes a file it writes itself, removes it in the same update; and every other write or edit of the artifact keeps it.
   An artifact whose location holds no identity file or an entry of any other form, such as an artifact stored before this rule, a folder, or a file that is not one such line, has the identity that its location gives, the first 32 hexadecimal digits of the SHA-256 of the location's UTF-8 bytes, which a move of it writes at the new location, so a store written before this rule needs no migration and merges as it did.
   No two locations of one tree have one identity: where two would, whether each holds the `id` in its file or one has it from its location, as with a file copied by hand or one written to hold another location's identity, each location whose file holds that `id` has the identity its location gives instead, and this repeats until no two locations of the tree have one; a sync reads each side's tree and the common base apart.
   A store shares an entry below `artifact-identity/` only as a regular file at the identity path of a location of the form §3 states, and a sync refuses an upstream that holds anything else there, such as a file at `artifact-identity/plans` or `artifact-identity/repositories/api`, where Prism keeps folders of identity files, as it refuses a file at `artifact-status/plans`.
   An entry that the store holds at an artifact's identity path, or in place of a folder above it, and that is no identity file of an artifact the store holds, such as a folder that a sync brought or the identity file of a location that holds no artifact, is no artifact's identity: an update that creates, moves, or removes an artifact replaces or removes it in the same update, so the update neither fails nor half applies over it, and a create at that path succeeds.
   A sync merges by identity rather than by path: a change that one side made to an artifact's bytes, its status record, or its comments belongs to the artifact whose identity that side holds at the change's location, and the merge gives each identity one location, the one at which both sides hold it, else the one to which one side moved it while the other kept it where the common base held it, else the upstream's where both sides moved it to different locations, else, where only one side holds it, the one at which that side holds it, unless the other side's removal of it stands, so that it takes none: the upstream's removal of an artifact always stands, and this machine's removal stands against every upstream change that left the artifact's bytes as the common base holds them, such as a comment, an approval asked, a request for changes, any other change of its status record alone, or a move to another scope, and gives way only to an upstream edit of its bytes, as approving it rewrites its status lines, after which each of its files takes the upstream's version there; every change to that artifact then merges at that location as if both sides had made it there, the identity file stays with the artifact's bytes wherever the merge keeps them, and every other location is left as the side that moved the artifact away or removed it left it.
   Each file of either side thus merges only at the location of the artifact it belongs to, or, where that artifact keeps no location and the file holds a change, is saved and named as below, so no location merges the files of two artifacts and no change is dropped unnamed, as where the upstream removed one artifact and moved another onto its location while this machine changed the moved one, whose change lands on the moved artifact there.
   There the bytes and the status record merge with Git's line merge against their version in the common base, so a file or status record that only one side changed takes that side's version, an approval answered on one machine while another moved the file lands on the moved file and its status record, and one that both sides changed and that does not merge, such as a status record, which is one line, keeps the upstream version and saves and names the local one as above; each comment lands there as §42 states.
   Where the merge would still leave two artifacts at one location, as where this machine removed an artifact and wrote or moved another to its path while the upstream edited the first one's bytes, or where both sides wrote or moved different artifacts to a location that the common base left empty, the location keeps the artifact whose identity the upstream holds there, with its identity, status record, and comments merged with every change that this machine made to it; the other artifact, where this machine moved it there from a location at which the upstream still holds it, goes back to that location with every change that this machine made to it, and otherwise each of its files there, its bytes, its status record, and each comment, that the common base does not hold alike is saved under the store's sync folder and named as above, so a change made on one file never lands on another file that a side wrote later at its path, whatever their bytes.
   So where this machine removed an artifact and wrote or moved another to its path while the upstream only commented on the first, asked its approval, or changed its status record alone, this machine's removal and its write or move stand, the later artifact keeps the path with its own identity, status record, and comments, and the upstream's change to the first is saved and named as below.
   A status record or comment that the merged store then holds at a location that holds no artifact, such as one changed on one machine while another removed the artifact, leaves the merged store, its bytes are saved under the store's sync folder, and the next tool result of each Prism server that uses the store names the path and scope label that its location gives and the saved copy, so none is lost and none stays where no reader shows it.
   A result that names a saved file from below `artifact-comments/`, here or as above, also quotes its line and text only when the saved file is a comment of the form §42 states, within every limit §42 sets, and names any other such file by its path, scope label, and saved copy alone, without any of its bytes, so a file that a sync brings puts no text before the agent that no reader would take as a comment.
   A comment of this machine's that a merge saves because its artifact's comment folder already holds the 1000 comments that §42 allows is named in a note of its own, apart from the comments of removed artifacts: the note says that the file holds the 1000 comments that a file may hold, quotes each comment's line and text only as the rule above allows, and does not say that the artifact was removed, since the store keeps the artifact and the comments that reached it first.

### Guidance

45.
