# Show a whole workspace in the review app

## Outcome

The review app opens a workspace, one record store, rather than one checkout: it lists workspaces only, combines every scope's artifacts for people and agents, adds a workspace from its store URL alone and keeps it in sync, shows code-repository content from clones Prism keeps, and shows a slice's verified files after a squash merge or force push.

## Design questions settled

- Component declarations come from the code repositories, never from a copy in the store: each code clone reads `.prism/workflow.md` on every remote branch, and a repository without code content shows only the component scope folders that the store holds, because a store copy of each branch's declaration would drift from the branches that §25 makes the source; cross-repository runs can add a store registration of components later without changing what this view shows.
- The app fetches an open workspace when its first page opens and then every 60 seconds while a page of it stays connected, and after a failed fetch it waits twice as long as before, up to 15 minutes, until a fetch succeeds, so an unreachable store costs at most one Git process every 15 minutes.
- The app's store commits carry the store clone's Git identity, which Git takes from the machine's configuration, or `Prism <prism@localhost>` when Git names none, as Prism's record commits already do, because the person's own name and host are already recorded in each action's history entry.
- The artifact index serves 20,000 artifacts and answers a listing within 1 second once built, a size well above any workspace Prism holds today and small enough to build in a test.
- Code clones live in the Prism application folder under `code/`, one bare blobless clone per repository remote, turned on and off by the person in the app per repository, and Prism sets no disk bound because a blobless clone keeps only the commits, trees, and the files people opened, while turning code content off deletes the clone.
- An SSH login name, such as the `git` of `git@github.com:acme/store.git`, is not a credential under [workspace-view.md§12](../../requirements/workspace-view.md#12), because SSH authenticates with the machine's keys and the name only selects the host's account, so refusing it would refuse nearly every SSH URL; a password in SSH user information and any user information in an HTTP or HTTPS URL, where it is how tokens are passed, are refused.
- An agent names a scope with a new `label` input, the scope label that listings report, so the existing `scope` and `component` inputs keep their meaning for writes; an unlabelled path that several scopes hold keeps the existing `artifact_ambiguous` refusal, which now names every scope of the workspace that holds it.
- Agents read every scope but change only their own checkout's scopes, the workspace, their repository, and its components, because §7 keeps where new artifacts go and no requirement lets one repository's agent change another repository's plans; a change to another repository's artifact is refused with a code of its own that names the scope.
- An artifact of a kind for which the agent's checkout configures no folder is listed with `path` null and its store `location`, which `get_artifact` also takes as input, because no checkout path can name it.
- The squash commit of a slice is the oldest commit on the first-parent history of the repository's default branch whose tree holds every verified file at its verified blob, looked for when the initiative ships; when none exists, as when the initiative ships before its branch merges, Prism records none and the slice page says that neither commit is available, rather than guessing.
- Existing "Shared records" entries become workspace entries because every checkout's workspace is derived from the store identity its configuration names, so no saved state needs rewriting; an old checkout-keyed URL answers with a redirect to its workspace URL and a store artifact's checkout path in it becomes its store identity, which serves bookmarks and tabs that reconnect after the upgrade.
- The last synced copy is the store's managed clone itself, so an unreachable upstream leaves every read working, as Prism's record reads already do; [workspace-artifacts.md§15](../../requirements/workspace-artifacts.md#15) refuses only a store that cannot be used at all, such as one whose first clone failed, so the two do not conflict.
- A store that holds no `artifacts/` folder yet, because no checkout has moved its artifacts, shows its records and a note that each repository keeps its artifacts in its checkouts until a Prism session there moves them.
- Markdown links in the store are mostly written for checkout paths, so a relative link resolves first against the artifact's store location and then, when nothing is there, through the artifact's checkout path under the configured paths of a checkout of its repository on this machine, or Prism's default paths where none exists, mapped back to a store location of the same scope or the workspace scope.
- The app pushes its own writes through the store sync that every record write already schedules, which [review-app-actions.md§10](../../requirements/review-app-actions.md#10) treats as part of changing records, so adding store-only workspaces adds no Git step to any action.
- Adding and removing a workspace and turning code content on or off change only the app's own state on this machine and no Prism record, so they are app routes with the page's write session and origin check rather than review app actions, which [review-app-actions.md§9](../../requirements/review-app-actions.md#9) reserves for changes to records.
- The recorded slice files of a verification run are the paths whose content differs between the slice's start content and the verified content, plus its frozen tests, because those are the files the slice changed; a slice started without start content records its frozen tests only and says so.

## Contract

Routes below are relative to the review app's viewer prefix `/session/<viewer token>`, and `<w>` is a workspace id.
A request that changes app state needs the page's write session in `X-Prism-Write` and a JSON body from the page's own origin, and is otherwise refused with `403` and `{ code, message }`, `code` `write_forbidden` or `origin_refused`, as action requests are.
Every JSON error answer of a route below is `{ code, message }`.

### Store identity

1. A store value is a network URL when it begins with `https://`, `http://`, `ssh://`, or `git://`, or has the scp form `[user@]host:path`; the store identity of an `https://`, `ssh://`, or scp-form value is its host in lowercase, a `/`, and its path without leading and trailing `/` and without one trailing `.git` in any letter case, with no scheme, user information, port, query, or fragment, so `https://github.com/Acme/store.git`, `ssh://git@GitHub.com:22/Acme/store`, and `git@github.com:Acme/store.git` all have the identity `github.com/Acme/store`.
   The store identity of an `http://` or `git://` value, which Git reaches without encryption, is its scheme, `://`, and that host-and-path identity, so `http://GitHub.com/Acme/store.git` has the identity `http://github.com/Acme/store` and `git://github.com/Acme/store.git` the identity `git://github.com/Acme/store`: a plaintext spelling never shares a clone or a workspace with an encrypted spelling of the same store, and plaintext spellings share one only with spellings of the same scheme.
   A folder path or `file://` URL has the identity `file:` followed by the real path of the folder.
2. A network store's managed clone is the folder `stores/<id>` of the Prism application folder, where `<id>` is the first 16 lowercase hexadecimal characters of the SHA-256 of the store identity, so every checkout and every added workspace that names any spelling of one store identity uses one clone and reads and writes the same records.
3. When `stores/<id>` does not exist and the folder that Prism 0.20 named for the same configured value exists, the first 16 hexadecimal characters of the SHA-256 of `<scheme>//<lowercase host and port><path>` for a URL, or `<lowercase host>:<path>` for the scp form, each path without trailing `/` and one trailing `.git`, and that folder is a Git clone whose origin has the same store identity, Prism renames it to `stores/<id>` before its first use, keeping its unpushed commits; a folder already at `stores/<id>` is used as before and the old folder stays untouched.

### Workspaces in the app

4. A workspace is one store identity on this machine, holding every registered checkout whose `.prism/workflow.md` names a store of that identity and the added workspace of that identity, if any; a registered checkout that names no store is a workspace of its own of kind `project`.
   A checkout on this machine is a checkout registered with the app or an entry of the machine's checkout list whose folder still holds a `.prism/workflow.md` that names that store and repository.
5. A workspace's id is the first 16 lowercase hexadecimal characters of the SHA-256 of `store:<identity>`, or of `project:<real path of the checkout>` for a workspace of kind `project`.
6. `GET /api/workspaces` answers `{ workspaces }`, one entry per workspace, live workspaces first, then by most recent use, then by name, each `{ id, name, kind, added, live, gates, store, repositories, checkouts, url }`: `kind` is `store` or `project`; `added` is whether a person added it from its store URL; `live` is whether a session holds a lease on one of its checkouts; `gates` counts its pending user gates, or is null when its records cannot be read; `store` is `{ identity, label, urls }` with `label` the store as messages name it without credentials and `urls` each URL this machine names it by, in the order first seen, or null for kind `project`; `repositories` lists `{ name, checkouts }` for each repository that the store registers or a checkout names, sorted by name, with the real paths of this machine's registered checkouts of it; `checkouts` lists every checkout path of the workspace; and `url` is the absolute URL of `/w/<id>/`.
   No field of an entry is a URL of a checkout, repository, or component.
7. A workspace's `name` is the workspace name that the store's roadmap record holds, else the last segment of its store identity without a trailing `.git`, else, for kind `project`, the name of the checkout's folder.
8. `GET /w/<w>/` answers the review page for that workspace, with the same places navigation as every page, and every `/w/<w>/api/...` route answers for that workspace what the same route of a checkout's page answers today, unless a clause below states otherwise; an unknown `<w>` answers `404`.
9. `GET /p/<project id>/<rest>` of a registered checkout answers `308` with `Location` the same `<rest>` and query under `/w/<w>/` of that checkout's workspace, with an `artifact` query value that names a store artifact by the checkout's path replaced by `store:<location>`; every other value is kept.
10. `GET /` answers `302` to `/w/<w>/` of the live workspace used most recently, else of the workspace used most recently, and, when the app lists no workspace, answers `200` with the review page in its no-workspace state, whose workspace list offers to add a workspace.
11. `POST /control/present` without `projectRoot` and with `open` true answers `{ url, open, writeGrant }` for the app's root URL as a present of a checkout does, and `POST /api/write-session` with `{ grant }` exchanges that grant for `{ token }` as a workspace page's own exchange does; `prism review --workspaces` opens that root URL with a write grant, from any folder.
12. `PUT /w/<w>/api/session` with an open tab that names a store artifact by a checkout path of the workspace stores it as `store:<location>`, and `GET /w/<w>/api/session` never answers a checkout path of a store artifact.
13. The workflow skill's **Workspace** term says that a workspace is one record store with every checkout and repository that shares it, that it is the review app's unit, and that a project without a store is a workspace of one.

### Adding and removing a workspace

14. `POST /api/workspaces` with `{ url, confirmEmpty }`, `confirmEmpty` optional and boolean, adds the workspace whose store the HTTPS, SSH, scp-form, or folder `url` names, and answers `200` with `{ workspace, merged }`, `workspace` its entry as `GET /api/workspaces` lists it with `added` true and `merged` false unless clause 19 applies.
15. An HTTP or HTTPS `url` that holds any user information before its host, or an SSH or scp-form `url` whose user information holds a `:` and so a password, is refused with `400` and code `url_has_credentials` before any Git command runs or any folder is made, and the message says that credentials come from the machine's Git configuration; an SSH login name such as the `git` of `git@github.com:acme/store.git` is no credential and is accepted, and a `url` that is no store value of clause 1 is refused with `400` and code `url_invalid`.
16. A network store is cloned with the machine's Git configuration and credential helpers into `stores/<id>` of clause 2, never asking on a terminal, and only the store is cloned; a store whose clone already exists on this machine is used without cloning.
17. When the clone fails, the add answers `502` with code `clone_failed` and a message that holds Git's reason with every user name, password, and token removed, and leaves no folder at `stores/<id>`, no temporary folder in `stores/`, and no workspace entry, while a folder that the add did not create stays unchanged: a folder at `stores/<id>` that is no clone of that store refuses the add with `409` and code `clone_folder_taken` and keeps its files.
18. A store repository that holds no commit is refused with `409` and code `store_empty`, keeping no folder and no entry, until the person adds it again with `confirmEmpty` true, which lists it named by clause 7.
19. When a newly cloned store has the root commit of a store that this machine already keeps under another identity that is no `http://` or `git://` identity of clause 1, the add removes the new clone, adds `url` to that workspace's `store.urls`, and answers that workspace with `merged` true.
20. An added workspace stays listed across restarts of the app until the person removes it, however many workspaces were used since and however long ago it was last used.
21. `DELETE /api/workspaces/<w>` of an added workspace answers `200` with `{ removed: true, clone, message }`: `clone` is `deleted` when no checkout on this machine names the store and the clone holds no commit that its upstream lacks and no uncommitted store file, else `kept`, with `message` naming the checkout path that names the store or saying that the clone holds changes that are not pushed; a workspace that is not added is refused with `409` and code `workspace_not_added`, and an unknown one with `404`.
   A removed workspace that still has registered checkouts stays listed with `added` false.

### Syncing a workspace

22. `startReviewApp` takes `workspaceFetchMs`, default 60000, and `workspaceFetchMaxMs`, default 900000.
    When the first page of a workspace with a network store connects its events stream `/w/<w>/api/events`, and again every `workspaceFetchMs` while a page of it stays connected, the app fetches and merges the store's upstream as a record store sync does, and it stops fetching when no page of it is connected; a read of `/w/<w>/api/index` starts no fetch, also for a workspace served through a registered checkout whose last fetch is old, while an agent's Prism server keeps fetching on its own record reads.
23. After a failed fetch, the next one waits twice as long as the wait before it, at most `workspaceFetchMaxMs`, and a fetch that succeeds restores the wait to `workspaceFetchMs`.
24. `/w/<w>/api/index` holds `sync`: `{ state, lastSyncedAt, lastAttemptAt, nextFetchAt, message }`, `state` `ok`, `syncing`, or `unreachable`, `lastSyncedAt` the time of the last fetch that succeeded or null, `lastAttemptAt` the time the last fetch started or null, `nextFetchAt` the time of the next timed fetch or null while no page is connected, and, while `unreachable`, `message` naming the store by its label and Git's reason without credentials, else null, while every page still reads the workspace from its managed clone.
25. A gate answer, comment, or approval that a person applies on a workspace's page is committed in its store and pushed to the store's upstream as a record write is, with the store clone's Git identity, or `Prism <prism@localhost>` when Git names none, also when no checkout of the workspace is registered.

### Agents read every scope

26. A `get_artifact` listing, without `path` or with a folder, lists the artifacts of every scope the store holds below that folder: the workspace scope, each repository folder `artifacts/repositories/<repository>/` with a valid repository name, and each component folder `components/<component>/` in one, each entry with `path`, `location`, `scope`, `kind`, `version`, `bytes`, and `status` where its kind has one, sorted by `path` with entries whose `path` is null last by `location`, and then by scope label.
27. An entry's `path` is the configured folder of its kind in the agent's checkout followed by the rest of its location below its scope's kind folder, or the configured `Glossary` or `Roadmap` path, or null when the checkout configures `n/a` or no path for its kind.
28. `get_artifact` takes `label`, a scope label as listings report it, and with `path` reads that scope's artifact at the kind and rest that the path names; a label that names no scope the store holds is refused with `scope_unknown` and `data.scopes` listing the labels it holds, and `label` together with `scope` or `component` is refused with `scope_invalid`.
29. `get_artifact` takes `location`, an artifact's location below `artifacts/`, in place of `path`, and reads the artifact there whatever the checkout configures; `location` with `path`, `label`, `scope`, or `component` is refused with `scope_invalid`.
30. A read by `path` without `label`, `scope`, or `component` that more than one scope of the store holds is refused with `artifact_ambiguous`, with `data.scopes` listing every holding scope's label in label order and a message that asks for `label`.
31. A write that creates an artifact, `expectedVersion` null, without `scope` takes the scope of the agent's own checkout as before, the scope among the workspace, its repository, and its components that holds the path's nearest folder, else the workspace scope, and no artifact of another repository's scope refuses it with `artifact_exists`.
32. A `write` with a version, `edit`, `remove`, `move_scope`, or `ask_approval` of a path that only scopes of other repositories hold is refused with `scope_not_writable`, `data.scope` the label of the first such scope, and a message that says to change it from a checkout of that repository.
33. A listing answers from an index of the store's artifacts that Prism refreshes at each store sync, at each artifact write of Prism's on this machine, and when the index is older than 60 seconds, without reading the artifacts that did not change; the result carries `indexedAt`, the ISO time of the index it answers from, a write is listed by the next listing, and a listing of a store of 20,000 artifacts answers within 1 second once its index is built.

### Every scope in the app

34. `/w/<w>/api/index` of a workspace of kind `store` lists in `artifacts` each store artifact of every scope as `store:<location>`, never by a checkout path, maps each in `artifactScopes` to its scope label, and holds `scopes`, `{ kind, label, repository, component, artifacts }` for each scope with at least one artifact, `repository` and `component` null where they do not apply, workspace first and then by label.
35. `/w/<w>/api/index?scopes=<label>,<label>` lists only the artifacts of those scopes, holds `scopeFilter` with the labels it applied and `unknownScopes` with the labels no scope has, and answers the same workspace id; the page keeps the filter in its URL's `scopes` parameter until the person changes it.
36. `/w/<w>/api/artifact?ref=store:<location>` answers the artifact as a checkout's artifact read does, with `ref`, `location`, and `scope`, and also when no checkout of the workspace is registered; an unknown location answers `404`.
37. An artifact answer holds `links`, `{ line, href, target, resolved }` for each relative Markdown link in its text in order, resolved first against the artifact's location and then through the artifact's checkout path under the configured paths of a registered checkout of its repository, or Prism's default paths without one: a path that those paths give an artifact kind maps to a location of the same scope or else the workspace scope, whose artifact the link names as `target` `store:<location>`, and a path they give no artifact kind names a code file of the artifact's repository, the repository of the checkout the page reads through for the workspace scope, as `target` `code:<repository>:<path>` when a registered checkout of that repository lists the path among its review sources or clause 50 resolves it from a code clone; `resolved` is true for each of these.
    When no checkout of that repository is registered on this machine and clause 50 does not resolve the link from a code clone, a link to a code file is not available on this machine: it holds `target` `code:<repository>:<path>`, or null for a workspace-scope artifact in a workspace with no checkout, `resolved` null, and `reason` `code_not_available`.
    Every other link names no artifact and no file and holds `target` null and `resolved` false, and `unresolvedLinks` counts only those.
    `/w/<w>/api/artifact?ref=code:<repository>:<path>` answers that file as a checkout's read of a review source does, with `ref` and `repository`, from a registered checkout of that repository whose review sources list the path, else from a code clone as clause 50 says, and `404` otherwise.
38. The page shows each artifact with its scope label in an element with `data-scope-label`, a scope filter that lists `scopes` in an element with `data-scope-filter`, each resolved link as a link that opens its `target` in a tab with `data-doc-link` naming it, each link to a code file not available on this machine marked with `data-link="unavailable"` and the words `not available on this machine`, and each unresolved link marked with `data-link="unresolved"` and the words `link not found`.
39. A store that holds no `artifacts/` folder answers `/w/<w>/api/index` with `notes` holding one note that names the store's registered repositories and says that each keeps its artifacts in its checkouts until a Prism session there moves them into the store.
40. A comment on a store artifact from a workspace page targets `artifact:<scope label>:<location below the scope folder>`, such as `artifact:api:requirements/billing.md`, and is applied like a comment from a checkout's page, its author named by the Git identity of the store clone and this machine's host.

### Code content

41. `PUT /w/<w>/api/code/<repository>` with `{ enabled: true }` clones the repository's first remote that the store's registration lists into `code/<id>.git` of the Prism application folder, `<id>` the first 16 hexadecimal characters of the SHA-256 of the remote's store identity, as a bare clone with `--filter=blob:none` that holds every branch of the remote as its own branch, and answers `200` with `{ repository, code }`, `code` `{ state: "on", branches, fetchedAt }` with `branches` `{ name, commit }` sorted by name; an unknown repository answers `404`, and one whose registration lists no remote `409` with code `no_remote`.
42. `{ enabled: false }` deletes the repository's code clone and answers `code` `{ state: "off" }`, and the set of repositories with code content on survives a restart of the app.
43. Each fetch of clause 22 also fetches every repository of the workspace whose code content is on, with every remote branch and removing branches that left the remote.
44. When a repository's remote cannot be fetched, its `code` is `{ state: "unreachable", message, fetchedAt }` with Git's reason without credentials, an earlier clone stays as it was, and an enable whose first clone fails keeps no clone folder.
45. `/w/<w>/api/index` lists `repositories`, `{ name, code }` for each repository of the workspace, `code` `{ state: "off" }` for one whose code content is off.
46. `GET /w/<w>/api/code/tree?repository=<r>&folder=<f>` answers `{ repository, folder, entries }`, each entry `{ path, type, branches }` for a file or folder directly in `folder` on any branch, `type` `file` or `folder`, `branches` `{ branch, blob }` sorted by branch with `blob` the file's Git blob hash or null for a folder, sorted by `path`.
47. `GET /w/<w>/api/code/file?repository=<r>&path=<p>` with `branch=<b>` or `commit=<c>` answers `{ repository, branch, commit, path, blob, bytes, content }` from the clone, `branch` null when read by commit, fetching the file's contents only then, so the clone holds no file contents that nobody opened; a path that the commit does not hold, a file over 512 KiB, a binary file, or a file that review sources leave out as a secret answers `404`.
48. `GET /w/<w>/api/code/components?repository=<r>` answers `{ repository, components, problems }`: `components` `{ identity, folder, branches }` for each component that `## Components` in `.prism/workflow.md` declares on any branch, `<repository>/<component>`, with the branches that declare it at that folder, sorted by identity and folder, and `problems` `{ branch, message }` for each branch whose declaration is invalid.
49. A branch that a fetch removed contributes nothing to `tree` and `components`.
50. No code route answers a URL of a Git host, and the page shows code content in its own pages, with each file's branch labels and no branch choice.
    A link of clause 37 to a code file whose path no registered checkout of its repository lists among its review sources resolves from that repository's code clone while its code content is on and the clone exists, at the remote's default branch, the branch that the remote's `HEAD` named at the clone's latest successful clone or fetch.
    When that branch holds the path as a file and review sources would not leave the path out as a secret by the path rule a checkout's review sources apply, such as `.env`, the link holds `target` `code:<repository>:<path>` and `resolved` true, and otherwise it answers as clause 37 says for a repository without a code clone, so the page never offers a link to a secret.
    A binary file or a file over 512 KiB still resolves and answers `404` only when opened, because telling those apart needs the file's contents, which the blobless clone fetches only on open.
    `/w/<w>/api/artifact?ref=code:<repository>:<path>` of a path that no registered checkout lists answers `{ ref, repository, branch, commit, path, blob, bytes, content }` from the clone at that branch as clause 47 reads a file, and `404` where clause 47 answers `404`, for a path the branch does not hold, a file over 512 KiB, a binary file, or a secret; a path that a registered checkout lists is still answered from that checkout as clause 37 says.
    The page opens such a link as a tab that shows the file with its branch's label in an element with `data-branch-label`.

### Verified files

51. Every verification run record of a slice, except one that stops at changed frozen tests, holds `files`, `{ path, blob }` sorted by path for each path whose content differs between the slice's start content and the content the run tested, plus each of its frozen tests, `blob` the Git blob hash of the tested bytes or null for a removed path, at most 2000 entries with `filesTruncated` true when more exist, and `filesFrom` `start-content`, or `frozen-tests` for a slice without start content, which records its frozen tests only; no run record holds file bytes.
52. A run record's `checkout` also holds `host`, this machine's host name up to its first `.`.
53. A `ship` operation of `update_roadmap` records in the initiative's decision `slices`, `{ <slug>: { repository, verified, shipped } }` for each done leaf slice with a passing verification run: `verified` that run's `checkout.head`, and `shipped` the oldest commit, among the at most 1000 newest of the first-parent history of the default branch of the shipping checkout's `origin`, `refs/remotes/origin/HEAD`, else `origin/main`, else `origin/master`, whose tree holds every recorded file at its blob and no removed path, after Prism fetches `origin` and ignores a failed fetch, or null when the run's repository is not the shipping checkout's or no commit qualifies.
    The ship result lists under `noShipCommit` the slugs whose `shipped` is null, and `get_roadmap` returns `slices` with the decision.

### Slice files

54. `GET /w/<w>/api/slice-files?initiative=<i>&slice=<s>` answers `{ initiative, slice, repository, verified, shipped, shown, files, message }` from the slice's latest passing verification run: `shown` is `{ commit, source }` with `source` `verified` while the verified commit is reachable from a branch of the repository's code clone, else `ship` while the commit recorded at ship is, else null; `files` lists `{ path, blob, shownBlob, state }` for each recorded file.
55. `state` is `same as verified` when `shownBlob` equals `blob`, `changed after verification` when they differ, and `not available` when `shown` is null; `shownBlob` is the blob at `shown.commit`, null where that commit does not hold the path.
56. When `shown` is null, `message` says that neither the verified commit nor a commit recorded at ship is in the repository's code clone, or, when its code content is off or unreachable, that the repository's code is not available on this machine; a slice without a passing run answers `files` empty and `message` saying so.
57. `/w/<w>/api/entity?ref=slice:<i>/<s>` holds `presence`, `{ source, branch, host, text }` for the slice's latest verification run when its verified commit is on no branch of the repository's code clone or its checkout was dirty, and for its live implementation claim, `source` `run` or `claim`, with `text` such as `in progress in feature-x on vm, not pushed` or `in progress on Claude on vm`, and no route answers the content of a commit that no branch of a code clone holds.

### Workspace search and checkout actions

58. `GET /w/<w>/api/search?q=<query>` answers `{ query, results, code, leftOut }`: `results` the store artifacts of every scope that match as a checkout's search matches today, each `{ ref, scope, matches }`; `code` the matches of the code of each component of a repository with a checkout on this machine whose index there is ready, as `search_repository_concepts` answers them, each with its `component`; and `leftOut` `{ component, reason }` sorted by component for every other component the workspace knows, `reason` `no_checkout`, `no_index`, or `search_failed`.
59. The components a workspace knows are the components of each checkout on this machine, each code clone's declared components, and each component scope folder of the store, with the root component `<repository>/<repository>` of each repository.
60. `/w/<w>/api/actions/targets?kind=index` lists index targets only for components of repositories with a checkout on this machine, and `/w/<w>/api/actions?target=index:<repository>/<component>` for any other repository is refused with `unknown_target`.
61. Every page of a workspace sits in the places navigation and is composed of review app UI kit elements and design values, so the kit guard reports nothing.

## Assumptions

- Probed: a bare clone with `--filter=blob:none` from a local bare repository holds commits and trees and no blobs when the source's upload-pack allows filters, and Git falls back to a full clone with the warning `filtering not recognized by server, ignoring` when it does not; reading `main:a.txt` with `git cat-file -p` then fetches that one blob on demand from the promisor remote (`git clone --bare --filter=blob:none --no-local --upload-pack='git -c uploadpack.allowFilter=true upload-pack' remote.git c2.git`, observed 3 commits, 4 trees, 0 blobs, and 1 blob after the read, Git 2.43.0).
- Probed: a bare clone with the refspec `+refs/heads/*:refs/heads/*` and `git fetch --prune` drops a branch that the remote deleted (observed `feature-x` gone after `git branch -D feature-x` in the remote).
- Probed: cloning a repository with no commit prints `warning: You appear to have cloned an empty repository.`, exits 0, and `git rev-parse --verify --quiet HEAD` exits 1 in the clone, which tells an empty store apart from a failure.
- Probed: a failed HTTPS clone names the URL without its user information in `fatal: unable to access 'https://127.0.0.1:9/x.git/'` and leaves no folder, and Prism's existing `withoutCredentials` removes user information from any URL Git prints otherwise.
- Probed: `url.<path>.insteadOf` in the Git configuration lets an HTTPS and an `ssh://<alias>/...` spelling reach one local repository, whose `git rev-list --max-parents=0` root commit is the same through both, which the acceptance tests use to stand in for a host and an SSH host alias.
- Probed: `git hash-object` of a file's bytes equals the blob id that `git ls-tree` and `git rev-parse <commit>:<path>` give for it (`ce013625030ba8dba906f756967f9e9ca394464a` for `hello\n` both ways).
- Unprobed: Git hosts other than local repositories serve partial clones; a host that does not is cloned in full, as Git itself falls back, so code content stays correct and only uses more disk.
- Unprobed: how teams order shipping and merging; a ship before the squash merge records `shipped` null, and the slice page then says that neither commit is available rather than showing another commit.
- Unprobed: code search hits for a component with a ready index come from the existing component search, which the acceptance suite cannot prepare without the native runtime; the suite checks the left-out components, and a component whose search fails is named in `leftOut` with `search_failed` rather than dropped.
