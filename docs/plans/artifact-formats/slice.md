# Artifact formats and migration

## Outcome

Every normative artifact type has one format with a conforming example, Prism reports the artifacts that break it and refuses work that cites them, and a person migrates an artifact behind a gate that shows every statement kept, moved out, or marked unknown.

## Contract

### Formats

1. Prism defines four artifact formats with the types `requirements`, `adr`, `glossary`, and `feature`, each with a whole-number version that starts at `1` and grows by one whenever its rules change.
2. Each format has one reference file, `skills/write-requirements/references/requirement-format.md`, `skills/write-adr/references/adr-format.md`, `skills/workflow/references/glossary-format.md`, and `skills/write-feature/references/feature-format.md`, which states `Format version: <n>` and `Example path: <path>`, lists every rule as one line `` - `<rule id>`: <rule> ``, lists each default value as one line `` - Default `<field>`: `<value>` `` under `## Defaults`, and holds one complete example as the only fenced block under `## Example`.
3. The rule ids that a reference lists are exactly the ids that the check reports for its format, each written `<type>.<name>`.
4. The four examples, written at their example paths in one project with default paths, are checked by `check_artifacts` with no finding and no unknown value.
5. The `requirements` format has the rules `requirements.text` (UTF-8 text of at most 1 MiB), `requirements.title` (the first line is `# <capability>`), `requirements.header` (`Status:`, `Created:`, and `Approved:` lines follow in that order before any section), `requirements.status` (`Draft`, `Approved`, `Withdrawn`, or `Superseded by <link>`), `requirements.dates` (Created is `YYYY-MM-DD`, and Approved is a date when the status is Approved and `n/a` when it is Draft), `requirements.sections` (`## Problem`, `## Goals`, `## Non-goals`, and `## Design questions` once each in that order before the first numbered section), `requirements.numbering` (each numbered section is `## <n>. <title>` directly after `<a id="<n>"></a>` with the same positive whole number, and no number repeats), `requirements.fields` (each numbered section holds `Pattern:`, `Disposition:`, `Requirement:`, `Rationale:`, and `Related:` once each in that order, with at most one optional `Supersedes:` line anywhere after `Disposition:`), `requirements.pattern` (`Ubiquitous`, `State-driven`, `Event-driven`, `Optional feature`, `Unwanted behavior`, or `Complex`), `requirements.disposition` (`Active`, `Withdrawn` optionally followed by a date and reason, or `Superseded by <link>`), and `requirements.links` (Related is `n/a` or comma-separated Markdown links whose targets are relative `.md` paths with an optional `#<anchor>`, or `#<anchor>` alone, optionally followed by one period).
6. The `adr` format has the rules `adr.text`, `adr.title` (the first line is `# <decision>`), `adr.header` (`Status:` and then `Created:` before any section), `adr.status` (`Proposed`, `Accepted`, `Declined`, or `Superseded by <link>`), `adr.dates` (Created is `YYYY-MM-DD`), `adr.sections` (`## Requirements`, `## Problem`, `## Decision`, `## Rationale`, `## Alternatives`, `## Consequences`, `## Mechanism`, and `## Decision Log` once each in that order, where only the Decision Log may be empty), and `adr.requirements` (the Requirements section is `n/a` or paragraphs or list items in which every Markdown link targets a relative `<path>.md` with an optional `#<anchor>`, while the reference's example and the skills write one link to `<path>.md#<anchor>` per list item).
7. The `feature` format has the rules `feature.text`, `feature.header` (the first line that is neither blank nor a comment is `Feature: <capability>`), `feature.rules` (at least one `Rule:`, and every `Example:` or `Scenario:` sits under one), `feature.requirement` (each Rule has, before its first example, at least one `# Requirement: [<title>](<path>.md#<anchor>)` comment, and may add `# ADR: [<title>](<path>.md)` comments), `feature.examples` (each Rule has at least one example), and `feature.steps` (each example has at least one `Given`, exactly one `When`, and at least one `Then`, in that order, where `And` and `But` continue the step before them).
8. The `glossary` format has the rules `glossary.text`, `glossary.title` (the first line is `# <name>`), `glossary.purpose` (one paragraph follows the title before the first term), `glossary.identity` (each term is `## <term>` directly after `<a id="<id>"></a>`, where the id is lowercase letters and digits joined by single hyphens and no id repeats), `glossary.definition` (the first paragraph after the heading is the definition, and its first sentence ends with a period and starts with none of `It`, `This`, `That`, `These`, `They`, or `See`), `glossary.fields` (after the definition and any further paragraphs come one `Source:` line, an optional `Aliases:` line of comma-separated names, and optional `Not to be confused with: [<term>](#<id>): <distinction>` lines whose id is another term of the glossary, and nothing else), `glossary.source` (Source is comma-separated sources, each a Markdown link, resolved from the glossary's folder, to a requirement section `<path>.md#<n>` or an ADR file, or `migration <id>`, or in a migration's proposed content `migration` alone, which stands for that migration), `glossary.source-decided` (each source resolves to a section of an Approved, Withdrawn, or Superseded requirement file, an Accepted or Superseded ADR, or an applied migration), and `glossary.source-withdrawn` (at least one source is in force: an Active section of an Approved file, an Accepted ADR, or an applied migration).
9. A `glossary.source-withdrawn` finding's message names every source of the term, and a `glossary.source-decided` finding names each source that is not decided and why: missing, Draft, Proposed, Declined, or a migration that was not applied.
10. Any required field value or required section body may be the single word `unknown`, which the check accepts and lists under the artifact's `unknowns` as `{ line, field }`, except the title, the status, and identities.

### Checking artifacts

11. `check_artifacts` takes `projectRoot`, optional `paths` of at most 500 project-relative files, and optional `type`, and without `paths` checks every artifact of a format: each `.md` file other than `README.md` up to four folders below the configured Requirements and ADRs paths, each `.feature` file up to four folders below the Feature files path, and the configured Glossary file, skipping any path the configuration turns off.
12. A given path is typed by the configured path it lies under, and a path under none of them is refused with `artifact_type_unknown`, and a path that does not exist with `artifact_missing`, each naming the path.
13. The result is `{ formats: [{ type, version, reference }], artifacts: [{ path, type, version, conforms, findings: [{ rule, line, message }], unknowns: [{ line, field }], earlierFormat, legacy }] }`, with formats in the order of clause 1 and artifacts ordered by that type order and then by path, where `line` is 1-based or null for the whole file.
14. `earlierFormat` is `{ version }` of the newest earlier version of the artifact's format that it conforms to when it breaks the current version, and null otherwise.
15. `dist/server/workflow/artifact-formats.mjs` exports `checkArtifactText(type, text, { formats })`, which returns `{ conforms, findings, earlierFormat }`, where `formats` defaults to Prism's own and otherwise lists, newest last, each `{ type, version, check }` whose `check(text)` returns findings.
16. `legacy` is `{ set, by, at }` of the legacy mark that covers the artifact's path while it breaks its format, and null when no mark covers it or it conforms.

### Attention and legacy marks

17. Attention holds `formats`, one entry per format in clause 1 order, `{ type, label, version, reference, count, earlier, artifacts: [{ path, findings, earlierFormat }], legacy: { count, sets: [{ id, by, at, count }] } }`, where `count` is the number of artifacts that break the format and no legacy mark covers, `earlier` is how many of them conform to an earlier version, `artifacts` lists those artifacts, and the labels are `Requirements`, `Decisions`, `Glossary`, and `Feature files`.
18. Each format entry whose `count` is above zero is also an Attention item `{ type: "format-findings", artifactType, label, count, earlier }` of the kind `formats`, the navigation counts these items under `kinds.formats`, and the page `attention:formats`, which the review link and `present_review` open, is labeled `Format findings`.
19. The Attention page shows each format item with its count, its artifacts that conform to an earlier Prism format under `Earlier Prism format` apart from the others under `No Prism format`, each artifact's path and each finding's rule and message, and its legacy count with who marked each set and when, built only from UI kit elements.
20. The review app action `artifacts.mark-legacy` on the target `artifacts:<type>` takes `paths`, a choice of several of the type's nonconforming artifacts that no mark covers, needs confirmation, and records a legacy set `{ id, type, paths, by: { name, email, checkout }, at }` with the applying checkout's Git identity, refusing an empty choice, or a path that conforms or is not of the type, with `invalid_input`.
21. The review app action `artifacts.remove-legacy` on the target `legacy:<set id>` removes that set and records who removed it and when, after which its artifacts count again.
22. A legacy set covers its paths until it is removed, also after their content changes, and an artifact that conforms is neither counted nor listed as legacy.
23. `/api/index` for a project with 300 nonconforming artifacts answers within 5 seconds, and a request made after one of them changes reports its new findings.

### Citing artifacts

24. An operation cites the requirement files of the references it adds through `update_initiative` `create`, `split`, `report_defect`, and `add_fix`, also inside `propose_design`, and through `update_roadmap` `add_initiative` and `update_initiative`.
25. `propose_design` and `accept_design` also cite each existing file under the configured Requirements, ADRs, Glossary, or Feature files paths that a Markdown link in the scope's `slice.md` or a planned slice's `slice.md` resolves to, and each frozen test that is a `.feature` file.
26. When an operation cites an existing artifact that breaks its format, legacy or not, Prism refuses the whole update with `artifact_nonconforming`, changing nothing, with `artifacts: [{ path, type, findings, legacy }]` and a message that names each artifact with its rule ids and ends `Ask for a migration of <path> in a session of its own.` for each, checking citations before every other check except argument validation.
27. A cited file that does not exist, and an `unknown` value, do not refuse an operation, and records that already cite a nonconforming artifact still load.

### Migration

28. `propose_migration` takes `projectRoot`, `type`, `source` and `target` project-relative paths, where `target` lies under the type's configured path and equals `source` for a migration in place, `content` (the whole migrated artifact), `summary` (plain text of 1 to 2000 characters on what changes and why), `leftovers` (`[{ statement, home }]`, each statement verbatim from the source and a proposed home of 1 to 500 characters), and optional `conflicts` (`[{ entry, content }]`).
29. Prism splits a source into statements: each paragraph, list item, blockquote line, and table cell outside the header row splits into sentences at `.`, `!`, or `?` followed by whitespace, each fenced code block is one statement, and headings, anchors, horizontal rules, and table separators are not statements, compared after replacing each Markdown link by its text, removing `*` and `_` emphasis markers, and collapsing whitespace.
30. A source statement that occurs in none of the normalized content, a leftover's statement, or a conflict's content refuses the proposal with `migration_unaccounted`, listing `statements: [{ text, line }]`.
31. A statement of the content that occurs in neither the normalized source nor an existing target refuses the proposal with `migration_invented`, listing `statements`, where the format's structure, a field value that is a format default, `unknown`, a link, or a date from the source file's Git history are not statements of the content.
32. Content that breaks its format, other than through `unknown` values, refuses the proposal with `artifact_nonconforming` naming the target.
33. When the source or an existing target has the status Approved or Accepted, content that changes its status, Created or Approved date, or drops or changes an identity it has refuses the proposal with `migration_changes_decision`, listing `changed: [{ field, before, after }]`, where a dropped or changed identity is `{ field: "identity", before: <identity>, after: <new identity or null> }`, while new identities for parts that had none are accepted.
34. Content must keep unchanged each entry of an existing target other than the source, where an entry is a requirement section by number, a glossary term by id, or a feature Rule by title, and the source's differing version of an entry goes under `conflicts` as a conforming entry of that identity, so content that changes a target entry, or a conflict that names no entry of the target or does not conform, refuses the proposal with `migration_conflict` naming the entries.
35. A pending migration of the same target refuses another proposal with `migration_pending`.
36. A proposal returns the migration `{ id, type, source, target, separateSource, summary, diff, targetDiff, leftovers, unknowns, conflicts: [{ entry, target, source }], status: "pending", proposedAt }`, where `id` matches `migration-<hex>`, `diff` is a unified diff from the source to the content, and `targetDiff` is one from an existing target to the content, or null.
37. `get_migration` takes `id` and returns that migration with its `answer` and `appliedAt`, and an unknown id is refused with `migration_unknown`.
38. A pending migration is an Attention item `{ type: "migration", id, artifactType, source, target, summary }` of the kind `questions`, and its page `migration:<id>`, which the review link and `present_review` open, shows the summary, the diff, each leftover with its home, each unknown value, each conflict's two entries side by side, and for a separate source the choice to remove it, built only from UI kit elements.
39. The review app action `migration.answer` on the target `migration:<id>` takes `decision` (`accept` or `decline`), one choice field `conflict:<entry>` per conflict between `target` (the default) and `source`, the toggle `removeSource` (off by default, offered only for a separate source), and an optional `note`, records the answer `{ decision, conflicts: { <entry>: "target" | "source" }, removeSource, note, by: { name, email, checkout }, at }`, and refuses an answered migration with `already_answered`.
40. `wait_for_user_gate` takes `migration` in place of `initiative` and gate ids, waits as it does for a gate, and returns `answered` with the migration's answer once the person answers.
41. `apply_migration` takes `id`, refuses a migration that is not accepted with `migration_not_accepted`, one whose source or target changed since the proposal with `migration_stale` naming the paths, and one already applied with `migration_applied`, and otherwise writes the content with each conflict's chosen entry and with the migration's id after each `migration` source that stands alone, removes a separate source only when the answer accepted its removal, records `appliedAt`, and returns `{ written, removed, acceptedBy, acceptedAt }`.

### Skills

42. A new `migrate` skill converts one artifact per session after a person asks or accepts an offer, reads the target format's reference and the source's Git history, marks values that neither gives as `unknown`, proposes through `propose_migration`, waits for the gate, applies through `apply_migration`, and commits only the written and removed paths in a commit of its own when commits are on.
43. `write-requirements`, `write-adr`, and `write-feature` link their format reference in place of their inline templates, `workflow` links the glossary format, and `setup` creates a missing glossary as that format's title and purpose.
44. `write-requirements` adds, in the change that records an approval, each term that the approved file or amendment introduces and the glossary lacks, with that requirement section as its source, and `ideate` no longer edits the glossary before approval.
45. `orchestrate` adds, in the change that accepts a Proposed ADR, each term that the ADR introduces and the glossary lacks, with that ADR as its source.
46. `workflow` tells every skill that finds an artifact breaking its format in a way `check_artifacts` did not report to report the artifact and the break to the person with an offer of migration and to leave it unchanged in that task.
47. `workflow` defines `Artifact format`, `Format finding`, `Legacy mark`, `Migration`, and `Leftover list` under Common terms.

## Assumptions

- Probed: Prism's own requirement files keep the field order and values of clause 5 (`grep -h "^Pattern:\|^Disposition:" docs/requirements/*.md`, observed only the six patterns and `Active`, `Withdrawn <date>: <reason>`, and `Superseded by [...]`).
- Probed: the shapes that Prism's `write-requirements` and `write-adr` templates before the formats legitimately produced conform to clauses 5 and 6, because those templates placed `Supersedes:` nowhere in particular, ended lines with a period, asked for "direct links" in an ADR's Requirements section without a list form, and left the Decision Log empty until a clarification (`git show 99a7cce:skills/write-adr/SKILL.md` and `git show 99a7cce:skills/write-requirements/SKILL.md`; the repository's history starts at that template, so no older Prism template is on record and no earlier format version is defined).
- Probed: with the rules of clauses 5 and 6 as now written, `checkArtifactText` over Prism's own `docs/requirements/` and `docs/ADRs/` reports 4 nonconforming files instead of 43, each a genuine break of the format and of the template: `docs/requirements/repository-intelligence-providers.md` (sections with several `Requirement:` lines and no `Related:`), `docs/requirements/review-app-ui-kit.md` (section 18 without its anchor), `docs/ADRs/plantuml-review/browser-rendered-plantuml.md` (no `## Problem` or `## Alternatives`), and `docs/ADRs/repository-intelligence/artifact-conservation.md` (no `Created:` and a Context, Decision, Consequences shape); the review demo's artifacts break every format, so Attention and citing refuse them until they change (a patched copy of the implemented checker run over both folders, observed the four files above with the findings named).
- Probed: the existing glossary parser reads table rows and headings as terms (`src/server/review/workspace-model.mjs` `glossaryEntries`), so a migrated glossary keeps showing its terms in Knowledge.
- Probed: Git reports a file's author dates with `git log --follow --format=%as -- <path>` in a fresh checkout (run in this repository on `docs/requirements/artifact-formats.md`, observed `2026-11-11`, the date of its one commit).
- Unprobed: a store that holds several glossaries for the workspace, a repository, and a component, which workspace artifacts introduce; until then each checkout checks its one configured glossary, and a term id that two glossaries a checkout sees define differently is reported as `glossary.identity` on both.
- Unprobed: sentence splitting of foreign prose, such as abbreviations followed by a capital; a statement split wrongly is reported as unaccounted or invented, never silently accepted.

## Before ship

- Prism's own nonconforming artifacts, the four files that the second probe names, are migrated after `artifact-skills` lands, one `migrate` session per file behind its migration gate, and the initiative ships only when `check_artifacts` in this repository reports no nonconforming requirement file or ADR.
- No slice holds these migrations, because each one is a session of its own that a person answers at its gate.
